## Context

The mobile app has to reach iOS Live Activities, WidgetKit, Android widgets and later Wear OS,
all of which are native code in every cross-platform framework; the Phase 0 plan (section 3)
chose React Native on Expo for the TypeScript end to end story and `expo-widgets`. Increment 9
turns that choice into a real app inside a workspace that was built for Node and Workers: pnpm
12 with the ISOLATED linker, Node 24, TypeScript 6.0, Vitest everywhere else. Facts that shape the
decision (`docs/increments/09-11-mobile.facts.md` sections 1 to 4):

1. Expo SDK 57 (`expo` 57.0.24) bundles React Native 0.86.3 and React 19.2.3
   ([bundledNativeModules.json](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo/bundledNativeModules.json)).
   Metro auto-configures for monorepos since SDK 52, so `metro.config.js` carries no
   `watchFolders`; Expo supports isolated installs from SDK 54 but warns that "some React Native
   libraries may cause build or resolution errors", with `nodeLinker: hoisted` as the escape
   hatch and `experiments.onDemandFilesystem` as the first thing to try
   ([monorepos guide](https://raw.githubusercontent.com/expo/expo/sdk-57/docs/pages/guides/monorepos.mdx)).
2. `expo prebuild` cleans by default in SDK 57; `ios/` and `android/` are build output.
3. Apps built with the iOS 27 SDK do not launch on iOS 27 without the scene lifecycle, which is
   the `expo-build-properties` option `ios.enableSceneSupport`, not an app-config key
   ([SDK 57 changelog](https://expo.dev/changelog/sdk-57)).
4. jest-expo 57.0.5 is Jest 29 throughout and needs `@react-native/jest-preset` 0.86.3 declared
   under the isolated linker ([jest-expo 57.0.5](https://registry.npmjs.org/jest-expo/57.0.5)).
5. The bundle identifiers are immutable once a build reaches a store, and each variant is its own
   app with its own App Group, associated domains and credentials (ADR 0005).

## Decision

We will build `apps/mobile` on Expo SDK 57 with Expo Router and continuous native generation
(`ios/` and `android/` are never committed), in three variants selected by `APP_VARIANT`
(`production`, `preview`, `development`), inside the pnpm 12 workspace with the isolated linker
kept, and test it with Jest on the plain `jest-expo` preset as ONE project.

1. **Development builds only.** No Expo Go: `expo-dev-client` builds for the `development` EAS
   profile (an iOS simulator build), `preview` is internal distribution, `production` auto-
   increments with `cli.appVersionSource: "remote"`. `runtimeVersion` uses the `fingerprint`
   policy so an update never reaches a build with a different native surface set. Each profile
   names its EAS environment (`development`, `preview`, `production`), whose variables
   (`SENTRY_DSN`, `SENTRY_ORG`, `SENTRY_PROJECT`, `GOOGLE_WEB_CLIENT_ID`, `GOOGLE_IOS_CLIENT_ID`,
   `EAS_PROJECT_ID`) are the build's config inputs, and its own `env` (`APP_VARIANT`,
   `APNS_ENVIRONMENT`). The shared `base` profile (increment 13) pins the SDK 57 images by full
   name, `macos-tahoe-26.5-xcode-26.6` with CocoaPods 1.17.0 and
   `ubuntu-26.04-jdk-17-ndk-r27b-sdk-57`, rather than the `auto` alias that moves with SDKs, so
   store builds, the native smoke's gate leg and local spikes use one toolchain; and sets
   `SENTRY_DISABLE_AUTO_UPLOAD` until a Sentry project exists (runbook step 18). `APPLE_TEAM_ID`,
   when set, becomes `ios.appleTeamId` for local device builds. The fingerprint hashes the whole resolved config, `extra` and plugin
   props included, so `mobile-preview.yml` publishes with `eas update --environment preview` and
   the preview profile's `env` repeated in the job (a test holds the two equal), to
   `--branch preview`, the branch the preview builds' channel serves; with any input missing the
   update carries a runtime version no build has and silently never applies (increment 9 review,
   expo-correctness-1). `eas update` requires `--environment` from SDK 55 anyway. Two inputs an
   update can never read are handled at the source (re-review, expo-correctness-1): `eas update
--environment` loads only Plain text and Sensitive EAS variables, so the six variables above
   are never given Secret visibility (README, owner tasks), and the `GOOGLE_SERVICES_JSON` FILE
   variable, which a builder receives as a path to a real file and an update not at all, is kept
   out of the fingerprint by a committed `fingerprint.config.js` that both read: it ignores the
   file each such variable names (relative to the project, the way @expo/fingerprint records an
   external file) plus the conventional `google-services*.json` and `GoogleService-Info*.plist`
   names. Verified with `expo-updates runtimeversion:resolve` (re-run below).
2. **APNs environment from the signing.** `aps-environment` and the expo-notifications `mode` come
   from `APNS_ENVIRONMENT`, which each EAS profile sets by distribution: `development` for the
   development profile, `production` for preview (ad hoc signed, which registers with production
   APNs like a store build) and production. A local build, development signed, defaults to
   `development`; on an EAS builder a missing value fails the config. The value rides in `extra`
   for `POST /v1/devices`' `pushEnvironment` (expo-correctness-4). Increment 11's
   `withApsEnvironment` writes this value, not one derived from the variant.
3. **Config.** `app.config.ts` is the one place the identifiers, entitlements, associated
   domains, intent filters and privacy manifests are written, with the plugin order the spec
   fixes and a local `plugins/withApsEnvironment.ts` reserved last (increment 11 implements it).
   `experiments.reactCompiler` is off, `experiments.typedRoutes` too (beta and opt-in in SDK 57),
   `platforms` is `ios` and `android` only (react-dom is installed for expo-router's peers, never
   rendered), `android.googleServicesFile` is added only when `GOOGLE_SERVICES_JSON` names one
   (spike 3), `android.blockedPermissions` removes the template's overlay and external-storage
   permissions and androidx.biometric's two, and expo-secure-store runs with
   `faceIDPermission: false` (the app never uses `requireAuthentication`). `metro.config.js` is
   exactly `getSentryExpoConfig(__dirname)`. The local package scripts (`start`, `ios`,
   `android`, `prebuild`) run the development variant; production and preview are built only
   through their EAS profiles.
4. **Isolated linker, no hoisting.** Every native package, and every package a native build
   phase or a config plugin resolves from `apps/mobile`, is a direct dependency pinned to Expo's
   own manifest version (or, outside the manifest, to the facts sheet's exact pin), rather than
   hoisting the workspace (spike 1 below). `scripts/toolchain-guard.mjs` asserts every
   `apps/mobile` dependency that `expo/bundledNativeModules.json` lists against its range, plus
   the exact pins (react-native-nitro-google-signin 2.3.0, react-native-nitro-modules 0.37.1,
   @maplibre/maplibre-react-native 11.4.0, jest 29.7.0, @sentry/react-native ~7.11.0), and CI's
   `test-mobile` job runs `expo install --check`; Renovate groups the manifest pins as
   `expo-sdk` and the exact pins for a quarterly review, never auto-merged.
5. **MapLibre is pinned, not linked, in Phase 0.** `react-native.config.js` sets its `ios` and
   `android` platforms to null and `app.config.ts` does not list its config plugin. Linked, its
   Android library merged `ACCESS_FINE_LOCATION` and `ACCESS_COARSE_LOCATION` into the manifest
   and its iOS pod (which calls `requestWhenInUseAuthorization`, with no purpose string in the
   app) plus the MapLibre Swift package went into every build, while the privacy manifest and the
   Play Data safety answers say the app uses no location (increment 9 review,
   expo-correctness-2). The maps increment deletes the entry, lists the plugin (the pod compiles
   only against the SDK the plugin adds, spike 1) and declares location truthfully.
6. **One owner for `get-session` on foreground.** The Better Auth client is created with
   `sessionOptions.refetchOnWindowFocus: false`: the Expo plugin's focus manager fires on every
   AppState change, background included, and refetched twice per foreground whatever the hourly
   throttle said. The hourly refresher refetches the session ATOM rather than calling
   `getSession()`, so its launch call joins the atom's own mount request; a transport-level Jest
   test on the real client counts one `get-session` at launch, none across background/foreground
   churn within the hour, one after it (increment 9 review, auth-and-store-8).
7. **Jest: one project on `jest-expo`.** Not the `jest-expo/ios` plus `jest-expo/android` pair,
   and not `jest-expo/universal`: the store code is written against a small synchronous
   `SqliteLike` interface and tested against Node's built-in `node:sqlite` in memory, so a second
   platform project would only run every file twice, and the web and node runners the universal
   preset adds would fail on the native modules. Pure logic that both sides share stays in
   `packages/shared` under Vitest. `.mjs` goes through the same Babel transform (Better Auth
   ships its client as `.mjs`), which lets one test run the REAL Better Auth Expo client over an
   in-memory SecureStore and a recorded fetch. `test-renderer` is `~1.2.0`, not the facts
   sheet's `~1.3.0`: 1.3.0 depends on react-reconciler ~0.34.0, which peers on React ^19.3.0,
   and 1.2.0's ~0.33.0 is the React 19.2 line.

## Spike results (increment 9, 2026-09-23, this machine: Xcode 27.0, JDK 21, Node 24.21.0)

Results with the full dependency set: `xcodebuild` for the iPhone 17 Pro simulator (iOS 26.5
runtime, iOS 27.0 SDK, Debug) **BUILD SUCCEEDED** (about 2 min incremental); `./gradlew
assembleDebug` for `arm64-v8a` **BUILD SUCCESSFUL**, 5 min 33 s cold and 1 min 38 s again with
the final set (866 tasks), the Android Gradle Plugin installing build-tools 36.0.0, CMake 3.22.1
and NDK 27.1.12297006 into the local SDK on first use. The development build installs and
launches on the iPhone 17 Pro simulator (`--initialUrl` pointing the dev launcher at Metro, which
bundles 2242 modules), migrates the expo-sqlite store (WAL, the bundled migration applied) and
reaches the sign-in screen. The Metro production export bundles the app (2084 modules) with the
`.sql` migrations inlined. The generated entitlements carry the variant's App Group, both
`applinks:` domains, `com.apple.developer.applesignin` and `aps-environment`, and the aggregated
`PrivacyInfo.xcprivacy` carries every reason declared in `app.config.ts` plus the pods' own.

One workspace side effect, also fixed without hoisting: `jest-expo` brings `jsdom` and
`@types/jsdom`, pnpm then links `jsdom` as Vitest's optional peer in every project (the lockfile
records that optional-peer resolution in every Vitest snapshot, which is expected), and
TypeScript reached `@types/jsdom` through the hidden hoist directory, whose
`/// <reference lib="dom" />` put the DOM lib into `apps/api`'s program and broke its
`BufferSource` types. `hoistPattern: ['*', '!@types/jsdom']` keeps it out.

Local native builds are `arm64` only (`-PreactNativeArchitectures=arm64-v8a` for Gradle, the
Apple silicon simulator for Xcode): this machine and its simulators are arm64, and the other ABIs
only multiply the build time. EAS builds every ABI a store build needs. Increment 11's
native-smoke job did too until 2026-09-30, when it moved to `x86_64` only, the ABI its emulator
launches: debug and release for all four ABIs ran the hosted Ubuntu runner out of disk, and every
scheduled run from 2026-09-24 to 2026-09-29 died inside the build with "No space left on device"
and no uploaded log. Measured on this machine, all four ABIs write 18.1 GB of build output against
5.8 GB for `x86_64` alone. The job now frees the preinstalled toolchains it never uses and checks
the free space before the build (25 GB on the runner; the script's local default is 10 GB plus 5
per ABI) and again before the emulator step downloads its system image (10 GB), so running out of
disk at those points is a readable failure rather than a runner that dies without a log.

### Spike 2: is the Hono client's async `headers` evaluated per request?

Yes, with hono 4.13.8: `hc`'s request builder awaits `opt.headers()` inside every call
(`dist/client/client.js`), and `__tests__/api-client-headers.test.ts` counts three evaluations
for three requests, each carrying the cookie value current at that moment. The `/v1` client
therefore reads `authClient.getCookie()` per request with no custom fetch wrapper, and a session
refreshed by `GET /api/auth/get-session` reaches the next `/v1` call at once.

### Spike 3: does an Android FCM token read need `google-services.json` in a dev build?

Yes. expo-notifications 57.0.20 answers `getDevicePushTokenAsync()` on Android from
`FirebaseMessaging.getInstance().token` (`PushTokenModule.kt`), and without
`android.googleServicesFile` `expo prebuild` applies no `com.google.gms.google-services` Gradle
plugin and ships no Firebase resources (the generated `android/` has neither), so there is no
default `FirebaseApp` and the call rejects with `ERR_NOTIFICATIONS_PUSH_REGISTRATION_FAILED`,
"Unable to get Firebase Messaging instance. Did you configure `googleServicesFile` path in app
config?". The FCM V1 credentials uploaded to EAS are the server's sending credentials and do not
reach the client. This was established from the module source and the generated project: the
one launch attempt on the `Pixel_10_Pro_Fold_-_EMU` AVD (a Google APIs Play Store image,
Android 37) stopped at adb authorization (`unauthorized`, the image waits for an on-device "Allow
USB debugging?" confirmation that a headless run cannot give), so the rejection was not observed
on a device. Consequence: `app.config.ts` takes an optional `GOOGLE_SERVICES_JSON` path (an EAS
file variable per variant; the Firebase project and its three Android apps are an owner task),
and `src/lib/push.ts` reports the token as unavailable instead of throwing until it is set. iOS
needs nothing extra: the APNs token comes from the `aps-environment` entitlement.

## Consequences

- Easier: one config file for three apps; native projects that can be regenerated at will; a
  store and sync core that is unit-tested in milliseconds without a simulator.
- Harder: every native library added later needs its config plugin in `app.config.ts` and its
  native peers pinned to Expo's manifest, or the build breaks in the isolated layout; the
  toolchain guard asserts the pins that matter. The real `expo-sqlite` binding, the SecureStore
  cookie jar and the native sign-in sheets are exercised only on a device.
- Reversibility: medium. Moving to `nodeLinker: hoisted` is a one-line change if a future
  library cannot be made to resolve; moving off Expo is a rewrite of the native layer.

## Alternatives considered

| Option                                            | Why not                                                                                              |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `nodeLinker: hoisted` for the whole workspace     | Not needed (spike 1), and it would let the API and the packages import undeclared dependencies again |
| `experiments.onDemandFilesystem`                  | Tried; it addresses Metro resolution outside `watchFolders`, not the Xcode phase that failed         |
| Committing `ios/` and `android/`                  | Every SDK upgrade and plugin change becomes a hand merge of generated projects                       |
| `jest-expo/ios` plus `jest-expo/android` projects | Doubles the suite for no coverage: the native modules are faked the same way in both                 |
| Vitest in `apps/mobile`                           | Unverified by Expo (facts section 1); jest-expo is what Expo supports                                |
| Expo Go                                           | Cannot load the native modules this app needs (nitro, Sentry, MapLibre, expo-widgets)                |
