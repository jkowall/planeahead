# 0006. UUIDv7 primary keys generated in `@planeahead/shared`

- Status: Accepted
- Date: 2026-09-19
- Deciders: @jkowall
- Supersedes: none
- Superseded by: none

## Context

Every Postgres table and every row the mobile app creates offline needs a primary key. The
key has to be mintable on the client (offline subscriptions and trips get an id before the
server sees them, and idempotent retries must reuse it), on the Worker, and by the database as a
default. It should sort by creation time so that append-only tables (`flight_events`,
`provider_calls`, `notifications`) get BRIN-friendly insertion order and cursor pagination
without a second column, and it must not leak a counter that reveals row volume.

Neon Postgres 18 ships a native `uuidv7()` function, so the database side needs no extension.
React Native does not expose `crypto.getRandomValues` without a polyfill, and Hermes has no
`crypto.randomUUID`.

## Decision

We will use UUIDv7 (RFC 9562 section 5.7) for every primary key, generated by `uuidv7()` in
`@planeahead/shared` with `uuidv7()` as the Postgres column default for rows the database
creates itself.

The generator is fixed as follows:

- 48-bit Unix millisecond timestamp, version nibble `7`, variant bits `10`.
- The 12 `rand_a` bits are a monotonic counter (RFC 9562 section 6.2 method 1): reseeded from
  the CSPRNG whenever the millisecond changes, incremented within a millisecond, seeded with
  the top bit clear so at least 2048 ids per millisecond are possible before the timestamp is
  bumped by one. A clock that runs backwards is treated as the same millisecond, so ids from
  one generator never sort before an earlier id.
- The 62 `rand_b` bits are random.
- Entropy comes only from `globalThis.crypto.getRandomValues`. If it is missing the function
  throws `MissingCryptoError` instead of degrading; the mobile app imports `expo-crypto` (or
  `react-native-get-random-values`) before any shared code runs.
- `uuidv7(now?)` takes an injectable clock; it is the only place in the package that defaults
  to `Date.now`.

## Consequences

- Easier: one id format on every tier, time-ordered inserts, cursor pagination on `id`, and
  offline-created rows that survive retries without a server round trip. `uuidv7Timestamp`
  gives a creation time for free in debugging.
- Harder: ids leak coarse creation time (millisecond) to anyone who sees them; that is
  acceptable for internal keys and is why user-facing tokens (`api_tokens`, share links) use
  random `pa_` prefixed secrets instead of exposing row ids. Client clocks can be wrong, so a
  row's `created_at` is set by the server or the database, never derived from the id.
- Commits us to 16-byte `uuid` columns and to a polyfill import order on mobile.
- Reversibility: low. Changing the id type after data exists means rewriting every primary and
  foreign key.

## Alternatives considered

| Option                           | Why not                                                                                              |
| -------------------------------- | ---------------------------------------------------------------------------------------------------- |
| UUIDv4                           | Random inserts scatter B-tree and BRIN locality on append-only tables; no time ordering for cursors. |
| ULID                             | Crockford base32 strings, not a native Postgres type; no standard, and PG18 has `uuidv7()` built in. |
| cuid2 / nanoid                   | Text keys, no native type, no time ordering.                                                         |
| `bigint` identity                | Cannot be minted offline; reveals row counts; needs a mapping for client-generated rows.             |
| Database-only `uuidv7()` default | Offline-created rows and idempotent retries need the id before the row reaches Postgres.             |
