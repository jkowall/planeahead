## 1. Questions answered

1. **Package version:** the SDK 57 catalog pins `expo-notifications ~57.0.20`; the lockfile and install resolve 57.0.20, whose Android side pulls `firebase-messaging 25.0.1` (facts 1, 2).
2. **iOS explicit permission:** `requestPermissionsAsync()` with no options asks for alert, badge and sound, and prompts only the first time (facts 7, 10).
3. **iOS provisional:** `ios.allowProvisional` grants silently, but expo reports it as `granted: false` (`ios.status` 3), and Apple delivers provisional notifications quietly to Notification Center only, even after "Keep" (facts 8, 9).
4. **Time-sensitive:** there is no permission option (deprecated in iOS 15); each push sets `aps.interruption-level: "time-sensitive"`, which needs the Time Sensitive Notifications capability (`com.apple.developer.usernotifications.time-sensitive`). No plugin in the repo writes it, and EAS capability sync supports it (facts 11 to 14).
5. **Android 13+:** the library merges `POST_NOTIFICATIONS`; at targetSdk 36 `requestPermissionsAsync` asks for it directly and needs no channel (Android doc and source), although Expo's page still says a channel must exist first (facts 3, 17, 18).
6. **Raw tokens:** on iOS `getDevicePushTokenAsync` returns the APNs token as lowercase hex with no Firebase involved; on Android it returns `FirebaseMessaging.getToken()`, and fails without `google-services.json` (facts 21, 22).
7. **Rotation events:** `addPushTokenListener` fires on every successful token read and on FCM `onNewToken` while JS is alive. It is not a complete rotation signal, so the app must re-read the token on every launch (facts 23 to 25).
8. **Android FCM prerequisites:** a Firebase project with one Android app per package, `google-services.json` through `android.googleServicesFile` (Expo applies the Google services Gradle plugin), and expo-notifications' own firebase-messaging dependency. The expo-notifications plugin only sets icon, colour and default-channel metadata (facts 26, 27, 41).
9. **iOS entitlements from plugins:** expo-notifications writes `aps-environment` only when the key is absent, and expo-widgets writes `development` unconditionally. `withApsEnvironment` has the last word, and nothing writes time-sensitive (facts 15, 16).
10. **Foreground presentation:** `setNotificationHandler` must answer within 3 s. With no handler the notification is not shown (fact 33).
11. **Tap deep link:** use `getLastNotificationResponse()` plus `addNotificationResponseReceivedListener` in a layout, call `router.push`, then `clearLastNotificationResponse()`. On iOS, `content.data` holds only the payload's top-level `body` dictionary (facts 34 to 37).
12. **Grouping per flight:** iOS uses `aps.thread-id`. Android cannot group per flight through expo-notifications or an FCM notification payload (no group support), and Android 16 auto-groups by app instead (facts 40, 52).
13. **Collapsing:** iOS uses `apns-collapse-id` (at most 64 bytes, and it becomes the request identifier). Android uses `android.notification.tag` plus `data.tag` (expo reads `data.tag`). FCM `collapse_key` only affects offline storage, with at most 4 keys (facts 39, 40, 42, 45, 46).
14. **Channels:** create the delay and gate-change channels at startup, because their importance is fixed after creation. FCM falls back to the manifest default and then to its own "Miscellaneous" channel (facts 39, 41, 48).
15. **Badge:** on iOS the badge is an absolute number and needs `allowBadge`; on Android it depends on the launcher (fact 50).
16. **Android 15 and 16:** Android's docs attribute notification cooldown to 15. A force stop blocks FCM until the app is reopened, notification taps are exempt from the background-launch limits, and 16 auto-groups notifications and tightens job quotas (facts 44, 51 to 56).
17. **iOS 26 and 27:** there are no User Notifications API changes since June 2024. Apple Intelligence summaries and prioritisation are per-app user settings, time-sensitive breaks through Summary and Focus, and push tokens are unreliable on the iOS 26.0 Simulator (facts 11, 57 to 60).
18. **Sign-out:** invalidate every token row of the installation server-side before `signOut`, for all kinds. Optionally also call `unregisterForNotificationsAsync()`: on Android it deletes the FCM token, and on iOS Apple now names logout as a reason to unregister (facts 61, 62, 64).
19. **Rotation hygiene:** POST the token on every launch and on every listener event. The server keeps only the newest row per device and kind, deletes on APNs 410 or FCM `UNREGISTERED`, and FCM expects a monthly refresh (facts 24, 25, 47, 63).
20. **FCM token future:** FCM is moving to Firebase Installation IDs (FIDs). The client token APIs have been deprecated since June 2026 and HTTP v1 `token` is deprecated but still accepted; expo-notifications 57.0.20 is token-only (facts 29 to 32).
21. **Repository state:** it reads the raw token, has the registration route and registers the push-to-start token. It lacks the foreground handler, tap routing, the token listener, launch re-registration, channels, the Android icon, provisional handling, sign-out invalidation and the time-sensitive entitlement (section 3).

### Tokens

21. [`EN/ios/ExpoNotifications/PushToken/PushTokenModule.swift:25-51`; `EN/ios/ExpoNotifications/Notifications/NotificationsAppDelegateSubscriber.swift:7-12,30-32`; checked 2026-09-30] On iOS, `getDevicePushTokenAsync` calls `UIApplication.registerForRemoteNotifications()` and resolves with the device token as lowercase hex (`%02hhx`); no Firebase is involved. A second call rejects the first pending promise (`E_PROMISE_REPLACED`).
22. [`EN/android/src/main/java/expo/modules/notifications/tokens/PushTokenModule.kt:54-71,87-97`; checked 2026-09-30] On Android it resolves `FirebaseMessaging.getInstance().token`. 23. [`PushTokenModule.swift:54-58`; `PushTokenModule.kt:23-34,68-69`; `EN/android/.../service/delegates/FirebaseMessagingDelegate.kt:100-105`; `EN/src/TokenEmitter.ts:9,43-48`; checked 2026-09-30] Every successful read also emits `onDevicePushToken`, so `addPushTokenListener` fires on reads as well as rotations; the docs warn that calling `getDevicePushTokenAsync` inside the listener can loop. An FCM `onNewToken` that arrives while no module exists is kept only as a static in-process value.
24. [ADOC `usernotifications/registering-your-app-with-apns` and `uikit/uiapplication/registerforremotenotifications()`; checked 2026-09-30] Apple: register "each time your app launches" and "Never cache device tokens in local storage." Tokens change on restore from backup, a new device or an OS reinstall. Registration works without user authorization; the pushes are then delivered silently.
25. [https://firebase.google.com/docs/cloud-messaging/android/client and https://firebase.google.com/docs/cloud-messaging/manage-tokens (both updated 2026-09-24); checked 2026-09-30] An FCM token changes on restore to a new device, a reinstall or cleared app data. Delete on `UNREGISTERED` (404), or `INVALID_ARGUMENT` (400) only when the payload is valid, and store an upload timestamp.
26. [@expo/config-plugins 57.0.9 `build/android/GoogleServices.js:45-47,87-134`; https://firebase.google.com/docs/android/google-services-plugin-and-file (updated 2026-09-24); checked 2026-09-30] `android.googleServicesFile` is copied to `android/app/google-services.json` and the `com.google.gms.google-services` plugin is applied. 32. [https://firebase.google.com/docs/cloud-messaging/manage-tokens; checked 2026-09-30] FCM is "transitioning from registration tokens to a registration system based on Firebase Installation IDs", and both are co-supported.

### Token hygiene

61. [ADOC `uikit/uiapplication/unregisterforremotenotifications()`; checked 2026-09-30] Apple: call it when "Someone logs out of an account associated with push notifications"; the app can always re-register.
62. [`PushTokenModule.swift:48-51`; `PushTokenModule.kt:73-84`; FirebaseMessaging reference; checked 2026-09-30] `unregisterForNotificationsAsync()` calls `unregisterForRemoteNotifications()` on iOS and `FirebaseMessaging.deleteToken()` on Android. With auto-init on, a new FCM token "will be generated the next time the app is started".
63. [`apps/api/src/routes/devices.ts:11-22,118-150`; `packages/db/src/schema/notifications.ts:74-100`; checked 2026-09-30] The API upserts `push_tokens` on `(kind, token)` and re-points a token to another user only from the same installation, clearing `invalidated_at`. Nothing enforces one live row per device and kind.
64. [ADOC `usernotifications/handling-notification-responses-from-apns`; https://firebase.google.com/docs/cloud-messaging/manage-tokens; checked 2026-09-30] Provider-side hygiene means 410 from APNs and `UNREGISTERED` from FCM. The client must re-register so that a token which becomes valid again gets `invalidated_at` cleared, which the route already does.

## 3. Conflicts with the repository (file:line)

1. **`apps/mobile/src/lib/push.ts:21-24`: provisional is treated as denied.** `requestPermissionsAsync()` (default alert, badge, sound) followed by `if (!permission.granted)` returns `denied` under iOS provisional, because expo reports `granted: false` (fact 8). Every call also re-requests instead of checking first, and it always asks for badge.
2. **`apps/mobile/src/lib/session.ts:116` and `apps/mobile/src/app/(app)/settings.tsx:125-131`: the token is registered only from a settings button.** Launch registration sends no token, and the Settings button is the only token registration, while Apple says to register each launch and never cache (fact 24). 4. **`packages/db/src/schema/notifications.ts:92` and `apps/api/src/routes/devices.ts:132-143`: rotated tokens stay live.** A rotated APNs or FCM token leaves the old row live, with the same shape as ADR 0008 item 7(b); the recorded fix is again scoped to push-to-start.

## 4. Design implications for Phase 1 (each with its trade-off)

1. **Wire contract for data.** Put app data in a top-level APNs `body` dictionary (for example `{flightSubscriptionId, kind, v}`) so expo exposes it as `content.data`. In FCM, send flat string `data` keys with no `body` key, and repeat `tag` and `channelId` inside `data` for the foreground path. Trade-off: this couples the sender to expo-notifications' Expo-format heuristics; the alternative is a client normaliser that reads `trigger.payload` on iOS and `trigger.remoteMessage.data` on Android, which is sender-agnostic but touches untyped fields (facts 36, 37, 39).
2. **Permission timing.** Ask for explicit authorization (alert and sound; badge only if a badge policy exists) in context, right after the first flight add, with a pre-prompt. Do not use provisional for delay and gate alerts. Trade-off: a lower opt-in rate, whereas provisional grants more but stays quiet even after "Keep" (fact 9). If provisional is adopted anyway, `push.ts` must accept `ios.status === 3` and later upgrade to an explicit prompt (UNVERIFIED item 3).
3. **Time-sensitive level.** Use time-sensitive for a gate change, and for a delay or cancellation inside the hour-around-departure window; send `active` otherwise. Add the entitlement to `ios.entitlements` for all three variants. Trade-off: it breaks through Focus and summaries, but Apple periodically asks users to re-evaluate it, and overuse gets it switched off; the entitlement also changes the fingerprint and needs a native build (facts 11 to 14).
4. **Token registration lifecycle.** On every session start and foreground with permission (granted, or provisional on iOS), call `getDevicePushTokenAsync` and `registerDevice`, and subscribe `addPushTokenListener`, guarded against re-entry. Trade-off: one cheap upsert per launch in exchange for no stale tokens; the listener fires on reads too, so debounce it (facts 23 to 25).
5. **Server-side rotation.** On registration, invalidate the other live rows of the same device and kind, or have the sender pick the newest row per device and kind. Trade-off: this forgoes multiple live tokens per device, which no platform needs (facts 25, 63).
6. **Sign-out.** Before `authClient.signOut()`, call an authenticated "invalidate this installation's tokens" endpoint covering every kind, `apns_live_activity_push_to_start` included. On Android, optionally also call `unregisterForNotificationsAsync()` (FCM `deleteToken`), which kills the token at FCM even offline, with a fresh token at next launch. Trade-off: offline sign-out cannot reach the server; iOS has no client-side equivalent that guarantees a dead token, so either block sign-out until the call succeeds or queue it keyed by install id (facts 61, 62).
7. **FCM identity.** Stay on legacy FCM registration tokens for Phase 1, sending through HTTP v1 `token` (deprecated but accepted), and never set `firebase_messaging_installation_id_enabled`, because that makes `getToken` throw. Keep `kind` open for a later `fcm_fid`. Trade-off: a deprecated path with no published removal date; the alternative is a custom native FID module outside expo-notifications (facts 29 to 31).
8. **Android message type.** Send notification-plus-data messages at high priority with `android.notification.channel_id`, `tag`, a `ttl` bounded by relevance, and `data.tag` and `data.channelId`. Trade-off: in the background FCM (or Play services) renders them without JS, reliably and without deprioritization, but loses per-message logic; data-only messages rely on expo's legacy background presentation path and risk deprioritization (facts 38, 39, 42, 43).
9. **Channels.** Create `flight_gate` (`HIGH`) and `flight_delay` (`HIGH`, or `DEFAULT` if delays should not use heads-up) at app start, before any permission request, and set plugin `defaultChannel` to one of them. Trade-off: importance is frozen at creation and IDs are effectively permanent (deleted channels stay counted), so decide the names and levels before the first build; two channels let users mute delays but keep gate alerts, at the cost of more settings surface (fact 48).
10. **Grouping and collapse.** Use iOS `thread-id` equal to the flight subscription id, and `apns-collapse-id` equal to `<subscriptionId>:<kind>` (under 64 bytes). On Android set `tag` (plus `data.tag`) to the same string, and accept app-level auto-grouping because no per-flight group is possible. Skip `collapse_key`, since its 4-key cap is lossy across flights, and rely on the tag plus TTL. Trade-off: no per-flight stacks on Android without custom native code (facts 40, 42, 45, 46, 52).
11. **Stale alerts.** Set `apns-expiration` and FCM `ttl` to the event's relevance window (for example until scheduled departure plus a margin), not the 30-day or 4-week defaults. Trade-off: a device offline past the window never sees the alert, but the in-app inbox (`notifications` table) still has it (facts 42, 45).
12. **Foreground handler.** Install `setNotificationHandler` once at module scope, showing banner, list and sound unless the flight's detail screen is open (then refresh in place); it must answer within 3 s. Trade-off: the answer must be synchronous-fast, with no network lookups (fact 33).
13. **Tap routing.** Add a root-level observer: `getLastNotificationResponse()` at mount, then the listener, `router.push('/flight/' + flightSubscriptionId)` once a session exists, and `clearLastNotificationResponse()`. Dismiss that flight's notifications on open using the collapse-id or tag identifier. Trade-off: the id must be the server subscription id; an unknown id needs a sync-then-fallback to home (facts 35, 45).
14. **Android notification icon.** Add `icon` (96x96 white on transparent) and `color` to the expo-notifications plugin. Trade-off: design work plus a native rebuild; without it the status-bar icon is FCM's default or the adaptive app icon (fact 41).
15. **Permission state.** Report the permission state (granted, provisional, denied) on `POST /v1/devices` and skip sends to devices without permission. Trade-off: an API field plus refreshing it on foreground; otherwise Android high-priority sends to non-displaying devices get deprioritized (facts 20, 43).
16. **Bursts.** Coalesce simultaneous changes for one flight (delay plus gate) into one notification server-side. Trade-off: a few seconds of latency, against Android cooldown damping repeats and iOS summaries condensing them (facts 51, 58).
17. **Badge.** Use no badge in Phase 1: omit `aps.badge`, and on iOS request alert and sound only. Trade-off: no unread cue, but no badge-reset bookkeeping (fact 50).

## 5. UNVERIFIED items and how to settle each

1. **Android 13+ prompt with no channel at targetSdk 36.** The source and the Android doc say it appears; Expo's doc says it does not. Settle: on an API 33 to 36 emulator with a fresh install, call `requestPermissionsAsync()` before creating any channel.
2. **Which Android versions ship notification cooldown on by default.** The official doc says 15, press says 16. Settle: check Settings > Notifications on API 35 and API 36 Pixel images, and send three pushes within 10 s.
3. **iOS upgrade from provisional.** It is unconfirmed that `requestPermissionsAsync` without `allowProvisional` shows the explicit prompt once the app holds provisional authorization. Settle on a device (expo 55.0.10 forwards repeated requests to the OS).
4. **Cold-start tap delivery with `enableSceneSupport: true` on an iOS 27 SDK build.** Settle: on a TestFlight or preview build, force-quit, tap a push, and confirm `getLastNotificationResponse()` returns it.
5. **Whether iOS calls `didRegisterForRemoteNotificationsWithDeviceToken` on its own for a rotated token without a register call.** Apple's docs are silent. This is mitigated by registering each launch; no cheap test exists.
6. **Removal date of HTTP v1 `token` and the deprecated client token APIs, and expo-notifications' FID plans.** Settle: watch the Firebase release notes and FCMDISC, and search expo/expo issues and PRs for FID support before SDK 58.
7. **Google Play services proxy display.** It is unconfirmed that proxied display honours the app's `channel_id`, `tag` and icon metadata. Settle: test on a Play-services device with the app backgrounded, and compare with `android.notification.proxy: DENY`.
8. **The small icon FCM uses when it drops an adaptive icon, and whether expo's app-icon fallback renders.** Settle: send a background notification to a build without the `icon` prop.
9. **FCM token retrieval before `POST_NOTIFICATIONS` is granted.** The source shows no gate. Settle: read the token on a fresh install before prompting.
10. **The Apple entitlement reference page for `com.apple.developer.usernotifications.time-sensitive`.** It was not retrievable; the key name comes from Expo's capability table and WWDC. Settle: an `eas build` log showing the capability synced, and the entitlement in the signed app (`codesign -d --entitlements`).
11. **Interaction of `thread-id`, `apns-collapse-id` and `relevance-score` with Apple Intelligence prioritisation.** It is undocumented. Settle: device observation only.
