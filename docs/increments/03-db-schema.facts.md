# Increment 3 facts (verified 2026-09-19)

Every fact below was checked against a primary source on 2026-09-19. Items the researcher could not confirm are tagged **(unverified)**. Where a fact contradicts `docs/increments/03-db-schema.md` or `docs/plans/phase0-plan.md`, it is marked **SPEC CONFLICT**.

## 1. Better Auth 1.7.5 schema

- 1.7.5 is the current npm `latest`, published 2026-09-14. No 1.7.6 exists. The pin stands. (https://registry.npmjs.org/better-auth)
- The canonical column list is `buildAuthTables` in `@better-auth/core`. The docs pages render fields from React components and cannot be fetched, so every column fact here comes from source. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/core/src/db/get-tables.ts)
- Required columns. `users`: name, email (unique), emailVerified (default false), image, createdAt, updatedAt. `sessions`: expiresAt, token (unique), createdAt, updatedAt, ipAddress, userAgent, userId (FK cascade). `accounts`: accountId, providerId, userId (FK cascade), accessToken, refreshToken, idToken, accessTokenExpiresAt, refreshTokenExpiresAt, scope, password, createdAt, updatedAt. `verifications`: identifier, value, expiresAt, createdAt, updatedAt. `rate_limits` (only when `rateLimit.storage = 'database'`): key (unique), count, lastRequest (bigint). Every table also needs `id`, injected by the adapter, not listed in `fields`. (same source, plus .../db/schema-diff.ts)
- 1.7.0 through 1.7.2 wrote an `accounts.issuer` column. 1.7.5 does not. A fresh schema must omit it. (.../db/schema-diff.ts)
- **SPEC CONFLICT.** `sessions.token` stores the plaintext 32-character token and is looked up by equality. There is no hashed-token option for the core session table. The convention line "presented tokens: token_hash bytea, never the token" cannot apply to `sessions`. Magic-link tokens can be hashed: `magicLink({ storeToken: 'hashed' })` hashes before writing to `verifications.identifier`. (.../better-auth/src/db/internal-adapter.ts, .../plugins/magic-link/index.ts)
- **SPEC CONFLICT, high severity.** Better Auth 1.7.x runs a runtime schema check on first use (`advanced.database.validateSchema`, on by default) and throws `SchemaMismatchError` for any column on those five tables that is NOT NULL, has no default, and is not written by Better Auth. Every PlaneAhead-owned extra column on `users`, `sessions`, `accounts`, `verifications`, `rate_limits` must be nullable or carry a DB default. A generated column counts as defaulted. (.../db/schema-diff.ts)
- The Drizzle adapter addresses tables by their **export key** and columns by their **TS property name**, never the SQL identifier. So TS keys stay camelCase, SQL names can be snake_case, and the auth-config `fields` mapping must NOT be used (it would force snake_case TS keys). (.../drizzle-adapter/src/schema-check.ts, .../db/adapter/get-field-name.ts)
- `usePlural: true` is literal string concatenation of `s`. Keys must be exactly `users`, `sessions`, `accounts`, `verifications`, `rateLimits`. The SQL table may still be named `rate_limits`. (.../db/adapter/get-model-name.ts)
- ids. The default generator emits a 32-character alphanumeric string that a `uuid` column rejects. `generateId: 'uuid'` works for normal inserts on pg (Better Auth omits `id` and the column default fires) but on the `forceAllowId` path it validates supplied ids against a UUID v1-to-v5 regex, rejects UUIDv7, warns, and silently substitutes a DB-generated id. A custom `generateId: () => uuidv7()` bypasses the gate and returns the value unchanged. (.../db/adapter/get-id-field.ts, .../core/src/utils/id.ts)
- OAuth tokens are written in plaintext to `accounts.accessToken/refreshToken/idToken`. There is no disable flag. The only built-in mitigation is `account.encryptOAuthTokens: true` (AES-256-GCM, default false). `account.updateAccountOnSignIn` defaults to true, so they refresh on every sign-in. (.../core/src/types/init-options.ts)
- Plugin surface is small. `anonymous` adds only `users.isAnonymous` (boolean NULL, default false) and creates a real user row with a synthetic `temp-<id>@<domain>` email, so budget orphan cleanup. `magicLink` and the Expo server plugin add nothing. OAuth state with `storeStateStrategy: 'database'` reuses `verifications`. (.../plugins/anonymous/schema.ts, .../plugins/expo/src/index.ts, .../better-auth/src/state.ts)
- Better Auth passes JavaScript `Date` objects for every `date` field on write; its own generator emits plain `timestamp()` in Drizzle `mode: 'date'`. Whether `timestamp({ withTimezone: true, mode: 'string' })` accepts a Date on INSERT is **(unverified)**. Reads are safe either way. Resolve with a one-row insert test, or exempt these five tables to `mode: 'date'`.
- Peer ranges: `drizzle-orm ^0.45.2 || >=1.0.0-rc.1`, `drizzle-kit >=0.31.4`. Both satisfied. (.../better-auth/package.json)

## 2. Drizzle and the Workers driver

- **SPEC CONFLICT.** The **array** form of the `pgTable` third argument is current; the object form has been deprecated since 0.36.0. Write every table as `pgTable('t', {...}, (t) => [ ... ])`. (https://github.com/drizzle-team/drizzle-orm/releases/tag/0.36.0)
- **SPEC CONFLICT.** Cloudflare's own Hyperdrive postgres.js example uses `{ max: 5, fetch_types: false, prepare: true }` and warns that `prepare: false` stops Hyperdrive caching prepared statements and adds round-trips. The `prepare: false` advice is PgBouncer folklore. `fetch_types: false` is only safe if no column uses a Postgres array type. (https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-drivers-and-libraries/postgres-js/)
- **SPEC CONFLICT.** Cloudflare states you do not need to call `client.end()` for Hyperdrive clients; cleanup is automatic at the end of a fetch, queue or Workflow invocation and on DO hibernation. The rule that still holds is: create the client inside the handler, never at module scope. Keep an explicit `end()` only on the non-Hyperdrive `DATABASE_URL` path (CI, drizzle-kit, `src/migrate.ts`). (https://developers.cloudflare.com/hyperdrive/concepts/connection-lifecycle/)
- Hyperdrive pools in **transaction mode** and RESETs connections on return. A `SET statement_timeout` will not survive a request; it must be issued inside the same transaction, or set with `ALTER ROLE`. Cloudflare also advises against wrapping operations in a transaction merely to hold SET state. (https://developers.cloudflare.com/hyperdrive/concepts/connection-pooling/)
- Drizzle docs state a generated column "cannot directly use in primary keys, foreign keys, or unique constraints". This collides with the required unique `flight_instances.flight_key`. Likely fix is `uniqueIndex()` rather than a unique constraint, but whether the restriction is Postgres-level or Drizzle-level is **(unverified)**. Prove it with a throwaway migration before writing 61 tables. (https://orm.drizzle.team/docs/generated-columns)
- Confirmed bug with direct impact: when drizzle-kit drops and recreates a generated column, Postgres cascades away dependent indexes and drizzle-kit does not recreate them. Fixed only in the 1.0 beta line, not 0.31.x. `generated-column.test.ts` should assert the `flight_key` unique index still exists after migrate. (https://github.com/drizzle-team/drizzle-orm/issues/4929)
- The migrator splits `.sql` files on the literal string `--> statement-breakpoint`. Put a marker between the `set_updated_at()` function and each `CREATE TRIGGER`, never inside the dollar-quoted body. Generate the file with `drizzle-kit generate --custom --name add_set_updated_at`. (drizzle-orm 0.45.2 `src/migrator.ts`; https://orm.drizzle.team/docs/drizzle-kit-generate)
- 1.0 is at rc.4 (2026-06-27) with no GA date published. Known 1.0 breaks that touch this increment: casing moves from the db instance to `snakeCase.table()`, and the migrations folder format changes (journal removed, per-migration folders). Writing explicit snake_case column names removes the casing exposure at zero cost. `check()`, `index`/`uniqueIndex`, `sql` defaults, `generatedAlwaysAs(sql)` and `$onUpdate` are unchanged (verified by absence from the breaking list, so high confidence rather than certainty). (https://orm.drizzle.team/docs/v0-v1-changes)
- Unknown: the exact SQL drizzle-kit 0.31.10 emits when a `check()` expression changes **(unverified)**. With every enumeration modelled as text + check, verify this early; a silent no-op would be a correctness hole. Related noise report: https://github.com/drizzle-team/drizzle-orm/issues/6256

## 3. Local Postgres 18 and CI

- `embedded-postgres@18.4.0-beta.17` (2026-06-05) ships real PostgreSQL 18.4 binaries inside the npm tarball for darwin-arm64 (148 MB) and linux-x64 (59 MB). No install-time download, no Docker, real TCP listener, so tests run through postgres.js. `server_version_num` returns 180004. (https://registry.npmjs.org/embedded-postgres, https://github.com/leinelissen/embedded-postgres)
- Only `initdb`, `pg_ctl` and `postgres` ship. No `psql`, no `pg_dump`. Any drift check must be SQL over the wire. (unpkg tarball listing)
- pnpm blocks postinstall by default and the package needs it to recreate symlinks. Root `package.json` must carry `pnpm.onlyBuiltDependencies: ["@embedded-postgres/darwin-arm64", "@embedded-postgres/linux-x64"]`. Runtime symlink hydration (issue #27) is still open.
- Open reliability issues: `initialise()`/`start()` can hang (#34) and `stop()` can never resolve (#32). Wrap all three in a `Promise.race` timeout in globalSetup and globalTeardown. (https://github.com/leinelissen/embedded-postgres/issues)
- Premise correction: PGlite is no longer PG17. `@electric-sql/pglite` 0.5.0 upgraded to Postgres 18.3, so it does have native `uuidv7()`. It remains the weaker fit because it is an in-process single-connection WASM build with no TCP listener, exercising `drizzle-orm/pglite` rather than postgres.js. Full schema parity under PGlite is **(unverified)**. (https://github.com/electric-sql/pglite CHANGELOG)
- CI: `postgres:18` and `postgres:18-alpine` both exist and are multi-arch, pushed 2026-09-18/19. Use the documented `pg_isready` health-check block and keep the `server_version_num >= 180000` assertion as a guard against the tag moving to 19. (https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers)
- `uuidv7()` is core in PG18, no extension. `server_version_num` is major*10000 + minor, so the guard rejects every PG17 minor. (https://www.postgresql.org/docs/18/release-18.html, .../runtime-config-preset.html)
- Neon branch actions exist (`neondatabase/create-branch-action` 6.3.1, `delete-branch-action` v3.2.1) with `branch_type: 'schema-only'` and `expires_at`. Pin by commit SHA; the newest tag drops the leading `v`. Free plan caps at 10 branches per project, which is the real constraint for a PR-per-branch flow.

## 4. Reference data and licensing

- OurAirports `airports.csv` (https://davidmegginson.github.io/ourairports-data/airports.csv): 12,725,082 bytes, 86,095 rows, Unlicense / public domain. `scheduled_service='yes'` plus large and medium airports is roughly 6,000 rows.
- **Process requirement.** Two downloads in this research session returned HTTP 200 with silently truncated bodies that still parsed as valid CSV/JSON. `scripts/fetch-seed-data.mjs` must compare downloaded bytes against `Content-Length`, fail loudly on mismatch, and write a SHA-256 manifest committed beside the data.
- Parse OurAirports by header name, not position: the live column order differs from the published data dictionary. The dictionary also says `closed_airport`; the live file uses `closed`. Observed type values: balloonport, closed, heliport, large_airport, medium_airport, seaplane_base, small_airport. (https://ourairports.com/help/data-dictionary.html)
- `ident` is unique across all rows. `iata_code` is populated on 9,055 rows with zero duplicates, supporting a partial unique index. `icao_code` is populated on only 10,510 rows, so store `COALESCE(icao_code, ident)` and flag which was used, because a `gps_code`-derived pseudo-ICAO will not resolve against AeroAPI.
- Timezones: mwgg/Airports `airports.json` (MIT, 29,307 entries, all with `tz`) covers 87.4 percent of scheduled-service airports, leaving 547 with no tz. Since `scheduled_departure_date` is origin-local and feeds the generated `flight_key`, the loader must **fail**, not warn, on a null tz. Fill the 547 with geo-tz at build time (devDependency only, never bundled). The small CC0 `tz-lookup` packages disagree with geo-tz on roughly 10 percent of inhabited points by the maintainer's own README, which is about 55 wrong timezones here. Not acceptable.
- geo-tz code is MIT but its boundary data is ODbL. Whether serving a derived tz string in an API response triggers ODbL attribution and share-alike is **(unverified and a legal question)**. Sidestep it by generating the 547 overrides once, reviewing them, and committing the reviewed list as curated data.
- Airlines: use vradarserver/standing-data `airlines.csv` (CC0, 5,964 rows, 5,904 with ICAO) as the ICAO/IATA spine, left-joined to OpenTravelData `optd_airlines.csv` (CC BY 4.0, caret-separated, filter `env_id=''`) for alliance and validity dates. OPTD alone is wrong: it has the wrong ICAO for Republic Airways (lists MEP, real code is RPA), and RPA is one of the named regional carriers. OPTD alliance values are dirty (`OneWorld` and `Oneworld`, plus one row whose alliance code is the literal string `2018-01-02`), so normalise before insert. Note the VRS files carry a UTF-8 BOM.
- Aircraft types: vradarserver `model-type/schema-01/*.csv` (CC0, 2,857 designators, updated daily) as the spine. Dedupe on ICAO preferring `IsActive=1`, drop the 137 fake designators starting with `-`, and note `WakeTurbulenceCode` carries two-value strings (`L/M`, `M/H`) and has no ICAO `J` (Super) category. Patch J from ColtJD45/icao-aircraft-designator-list (MIT, complete, but a frozen 2025-08-19 snapshot).
- ICAO Doc 8643 has no free machine-readable endpoint: the old `www4.icao.int` JSON returns a 302 with an empty body and `cfapps.icao.int` returns 404. Do not build against it. FAA Order JO 7360.1K is public domain but PDF-only and unparsed **(unverified as a loader input)**.
- The spec's "icao-aircraft-types npm package" does not exist. That line should be struck.
- **regional_operators has no source.** No authoritative published table of AA/DL/UA regional flight-number blocks exists; the only range claims found are unsourced forum posts, and blocks are reassigned at schedule changes. The verifiable substitute is the BTS Marketing Carrier On-Time Performance table, which carries marketing carrier, marketing flight number, operating carrier and operating flight number on every row from January 2018 to June 2026. That means observed ranges with validity dates, an observation count and a confidence flag, refreshed monthly. Safe because `DesignatorResolver` makes the authoritative AeroDataBox call, so this table is a display hint, never a source of truth for `flight_key`. BTS licensing is presumptively public domain as a US DOT work but **(unverified)**.
- Ruled out: OpenSky aircraft database (registration-level not type-level, 108 MB, latest snapshot 2025-08, license **unverified**, returns 403 to automated fetches) and rikgale/ICAOList (no license at all).

## 5. Neon and Hyperdrive limits

- Hyperdrive opens roughly 100 origin connections per config on Workers Paid, 20 on Free. Cloudflare states the limit is soft and may be exceeded. Configurable per config with `--origin-connection-limit`, floor 5. Other limits: 15 s connect timeout, 10 min idle, 60 s max query, 25 configs per Paid account. (https://developers.cloudflare.com/hyperdrive/platform/limits/)
- **Budget arithmetic in plan section 5 is wrong.** Neon reserves 7 connections for the superuser, so 0.25 CU gives 97 usable against a soft ~100, not 104. At 0.5 CU it is 202 of 209. (https://neon.com/docs/connect/connection-pooling)
- Use the Neon **direct** endpoint, not `-pooler`. Cloudflare's setup guide says to uncheck connection pooling, and Neon explicitly recommends against combining its PgBouncer with Hyperdrive. Neon's pooler is transaction mode and rejects `SET`, which would silently drop any `statement_timeout`. (https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-database-providers/neon/, https://neon.com/blog/hyperdrive-neon-faq)
- Hyperdrive is included on Free and Paid at no extra charge; caching is disabled per config with `--caching-disabled`. Default TTLs when enabled are 60 s max_age, 15 s swr. (https://developers.cloudflare.com/hyperdrive/platform/pricing/, .../configuration/query-caching/)
- `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_DB` is correct and takes precedence over `localConnectionString`. With `wrangler dev` local, pooling and caching do not apply; the Worker connects directly, so include `sslmode=require` in the Neon URL yourself. A Hyperdrive-issued local string carries `sslmode=disable`, which makes postgres.js throw. (https://developers.cloudflare.com/hyperdrive/configuration/local-development/, https://neon.com/docs/guides/cloudflare-hyperdrive)
- A Worker invocation can have at most six connections simultaneously waiting for response headers. This is the stated reason for `max: 5`. (https://developers.cloudflare.com/workers/platform/limits/)
- Neon PG18 is supported and selectable at project creation (currently 18.6). Major version changes later require a new project plus migration, so pick 18 at creation. Whether PG18 is the **default** for new projects, and whether it is still labelled preview, are both **(unverified)**; pass the version explicitly. (https://neon.com/docs/postgresql/postgres-version-support)
- Restore window: Free 6 hours max, Launch default 1 day and max 7 days, Scale max 30 days. The setting is project-wide. Scale to zero is 5 minutes and cannot be disabled on Free. (https://neon.com/docs/introduction/restore-window, .../scale-to-zero)
- Whether Neon permits `ALTER ROLE <role> SET statement_timeout` is **(unverified)**. Neon documents that any `context = 'user'` parameter is settable and `statement_timeout` is in that class, but no Neon page names it. Test on the dev branch before relying on it.
- Cloudflare names node-postgres as the recommended Hyperdrive driver with "the best compatibility with Hyperdrive's caching", with postgres.js "also supported". The spec picks postgres.js; that deserves an explicit ADR sentence rather than an implicit choice.

## Decisions the orchestrator must take

1. **Local Postgres 18.** Recommend `embedded-postgres@18.4.0-beta.17` with a Vitest globalSetup. Trade-off: real PG 18.4 over TCP and the real postgres.js path, at the cost of a 148 MB dev dependency and two open hang bugs that force explicit timeouts.
2. **Better Auth id generation.** Recommend `advanced.database.generateId: () => uuidv7()`, not the literal `'uuid'`. Trade-off: keeps ADR 0003's app-supplies-the-id rule and avoids the v1-to-v5 regex silently replacing UUIDv7 ids, at the cost of a custom function instead of a one-word setting.
3. **usePlural and schema keys.** Recommend `usePlural: true` with an explicit five-key object `{ users, sessions, accounts, verifications, rateLimits }` and SQL table `rate_limits`. Trade-off: one camelCase key that does not match the SQL name, versus adding a `rateLimit.modelName` config line.
4. **Timestamp mode on the five auth tables.** Recommend testing `mode: 'string'` with a real insert before freezing; fall back to `mode: 'date'` for those tables only. Trade-off: one exemption to the timestamptz convention versus an unverified write path under Better Auth's Date objects.
5. **Refresh token storage.** Recommend keeping our own `refresh_token_enc` + key version for the Apple native route, enabling `account.encryptOAuthTokens: true`, and documenting Better Auth's own token columns as Better Auth-owned. Trade-off: two encrypted stores with different key schemes versus plaintext OAuth tokens in `accounts`.
6. **postgres.js options.** Recommend `{ max: 5, fetch_types: false, prepare: true }` and dropping `ctx.waitUntil(client.end())` on the Hyperdrive path. Trade-off: contradicts the written spec, but matches Cloudflare's current documentation and keeps Hyperdrive's statement cache working.
7. **Connection budget.** Recommend production Neon at 0.5 CU and an explicit `--origin-connection-limit` (80 for dev/staging). Trade-off: a little more spend versus a soft Hyperdrive ceiling that exceeds usable connections at 0.25 CU.
8. **Commit seed data files.** Recommend committing OurAirports, mwgg, VRS airlines and VRS model-type, plus a SHA-256 manifest, with the geo-tz overrides committed as reviewed curated data. Trade-off: roughly 23 MB in the repo and a manual refresh cadence, in exchange for reproducible builds and no ODbL exposure from a build-time derivation.
9. **regional_operators in increment 3.** Recommend creating the table empty and deferring the loader to the BTS import increment. Trade-off: an unpopulated table in Phase 0 versus blocking on a seed source that does not exist.
10. **pgTable third argument.** Recommend the array form everywhere. No trade-off; the object form is the deprecated one.
11. **Explicit snake_case column names.** Recommend writing them out rather than relying on the `casing` option. Trade-off: more typing now, one entire category of 1.0 upgrade work removed.
12. **Migration path.** Recommend asserting in `src/migrate.ts` that migrations never run through the Hyperdrive binding. Trade-off: none; Hyperdrive's 60 s statement cap and transaction-mode pooling are wrong for DDL.

## Appendix: open questions per research topic

### better-auth-schema (37 facts, 0 unverified)

- Does Drizzle timestamp({ withTimezone: true, mode: 'string' }) accept a JavaScript Date on INSERT? Better Auth passes Date objects for every 'date' field, and its own generator emits plain timestamp() in Drizzle's default mode:'date'. Increment 3 mandates timestamptz with mode:'string' for every instant. Reads are safe either way because the adapter's customTransformOutput does new Date(data), but the write path is unverified. Resolve by a one-row insert test against PG18, or exempt the five Better Auth tables and use timestamp({ withTimezone: true, mode: 'date' }) there. Not verified from source or docs.
- Does postgres.js return the rate_limits.lastRequest bigint as a JavaScript number through Drizzle's bigint({ mode: 'number' })? postgres.js returns int8 as a string by default and Drizzle's mode:'number' is supposed to parse it, but this was not verified for the Hyperdrive/postgres.js combination. Better Auth compares lastRequest arithmetically, so a string would silently break rate limiting. Alternative: set rateLimit.storage to 'secondary-storage' backed by a Durable Object or KV and drop the table entirely, which also avoids a Postgres write on every auth request from a Worker.
- Which endpoints actually set forceAllowId: true? It was not traced through the 1.7.5 call graph. It matters only if generateId is left as the literal 'uuid'; the recommended custom uuidv7 function makes the question moot.
- Does the rate-limit writer supply an id on insert, or does it rely on the column default? diffSchema requires the id column to exist on rate_limits, but the write path was not read. With uuid DEFAULT uuidv7() on the column this cannot fail either way.
- Whether account.encryptOAuthTokens uses options.secret or a separate key, and how it interacts with our envelope-crypto key-version scheme from increment 5. The option's key derivation was not read at v1.7.5; check packages/better-auth/src/crypto before deciding whether to rely on it or to keep our own refresh_token_enc column as the only encrypted store.
- Whether passing the FULL PlaneAhead schema object (61 tables) to drizzleAdapter instead of a 5-key subset causes any problem. diffSchema only iterates expected tables so extra tables are ignored, and getSchema looks up by key, but this was not tested; a table accidentally exported under a key like 'users' twice would collide. Passing an explicit 5-key object avoids the question entirely.
- The published docs pages (concepts/database, plugins/anonymous, core schema) render their field tables from React components, so no field-level fact in this sheet could be corroborated against a rendered docs page. Every column fact here comes from the v1.7.5 source. If schema-review.md needs a docs citation rather than a source citation, the docs pages will have to be read in a browser rather than fetched.

### drizzle-api (26 facts, 0 unverified)

Needs a throwaway migration against the real PG18 Neon branch before the schema is written.

- Is drizzle-kit 0.31.10 free of the expression-index and generated-column re-diff noise reported in issue #6256 for the generate path (the report is about push)? The 'db:generate produces no diff' acceptance criterion depends on it.
- Is there a published 1.0.0 GA target date? None found. rc.4 has been the head since 2026-06-27 with only commit snapshots since, so the upgrade window is unknown and should not be assumed to fall inside Phase 0.
- Does drizzle-kit 1.0 remove the object-form pgTable third argument outright, or merely keep it deprecated? The v0-v1 change list does not mention it either way.
- Does Better Auth 1.7.5's Drizzle adapter emit or expect the array-form third argument, and does it assume a particular casing configuration? This determines whether the users/sessions/accounts/verifications/rate_limits tables can share the project's column helpers or need a separate convention.
- Confirm by running `npx drizzle-kit@0.31.10 --help` that `check` and `generate --custom` are present in 0.31.10 specifically. The docs site now serves v1 content, so both were verified against v1 docs plus version history rather than a 0.31 page.
- What bytea round-trip behaviour does drizzle-orm 0.45.2 have over postgres.js specifically? rc.1 fixed bytea data corruption on neon-http, which shows bytea mapping is driver-sensitive, and the schema depends on bytea for every encrypted secret and every token hash.

### reference-data (31 facts, 0 unverified)

- ODbL scope on derived timezone strings. geo-tz's boundary data is ODbL (code is MIT). A per-airport IANA tz string derived from those boundaries is arguably a Derivative Database, and ODbL 4.4(b) 'Publicly Use' may be triggered by serving that tz in an API response, pulling in attribution and share-alike obligations. Storing it in a private repo is clearly fine. Serving it is not a question I can answer and I will not guess. Either get an owner/counsel call, or sidestep it by generating the 547 overrides with geo-tz once, reviewing them, and committing the reviewed list as hand-curated data.
- OpenSky license is unverified. https://opensky-network.org/data/datasets returns HTTP 403 to automated fetches and served no license text via curl. If the `aircraft` table (registration + hex + validity ranges) is to be seeded from OpenSky, someone must read the terms in a browser first. Do not commit OpenSky data before that. Also note the latest snapshot is 2025-08 and no 2026 snapshot exists, so it is ~13 months stale regardless.
- BTS transtats license is presumptive, not verified. As a work of the US DOT the On-Time Performance data is presumptively public domain, but I found no explicit license or terms statement on transtats.bts.gov. Worth confirming before committing derived BTS aggregates, given that bts_carrier_flight_monthly, bts_route_monthly and bts_airport_hourly are all in the schema.
- How many airports should the airports table actually hold? The spec does not say. 86,095 rows is everything OurAirports has; scheduled_service='yes' plus large and medium is roughly 6,000. Importing all 86k makes the tz problem 14x larger for airports nobody will ever fly from, but a narrow filter means a user adding an obscure charter leg hits a missing airport. Recommend the ~6,000-row filter plus a runtime upsert path that pulls a single airport from OurAirports on demand, but this is a product call.
- Does aircraft_types.wake_turbulence need the four-value ICAO set including J (Super)? VRS encodes only L, M, H, L/M, M/H. If J matters for A388-class aircraft, it comes from ColtJD45 (2 rows) or hand-curation. Also needs a decision on whether the two-value strings L/M and M/H are stored as-is or collapsed, since that determines the check() constraint.
- I did not parse FAA Order JO 7360.1K. I verified only that the PDF is live, public domain and 11,971,409 bytes. Its exact column set and row count are unverified. If it is to be the tie-breaker when VRS and ColtJD45 disagree, someone needs to confirm a table extraction actually works on it.
- The spec names an 'icao-aircraft-types npm package'. No package by that name exists on npm. That line should be struck from docs/increments/03-db-schema.md.
- Should regional_operators ship at all in Increment 3? Since DesignatorResolver authoritatively resolves the operating carrier on the first call, and the BTS-derived mapping needs a monthly refresh job that is not in Phase 0 scope, an alternative is to create the table empty in Increment 3 and defer the loader to the increment that builds the BTS import. That keeps Increment 3 from depending on a data source that has no seed file.

### neon-hyperdrive-limits (23 facts, 1 unverified)

- Does Neon actually allow ALTER ROLE <role> SET statement_timeout? Neon documents that any parameter with context = 'user' can be set per session, database or role, and statement_timeout is context = 'user' in Postgres, but no Neon page names statement_timeout. Verify on the dev branch: SELECT context FROM pg_settings WHERE name='statement_timeout'; then ALTER ROLE hyperdrive_user SET statement_timeout='10s'; then reconnect and SHOW statement_timeout. If the role-level setting sticks it is the right place for the timeout, and withDb does not need to SET anything per request.
- What is Hyperdrive's DEFAULT origin connection limit when --origin-connection-limit is not passed? The docs give a floor (5) and a plan-dependent ceiling (~100 Paid) but never state the default. Determine it empirically or from the API response for the created config, then pin the value explicitly per environment rather than relying on the default.
- Does the schema use any Postgres array type? Cloudflare's fetch_types: false optimisation saves a round-trip only if it does not. Answer this while writing src/schema/ and record the decision in schema-review.md; if arrays appear anywhere, fetch_types must be true or the driver will fail to parse those columns.
- Should the driver be node-postgres (pg) rather than postgres.js? Cloudflare names pg as the recommended driver with "the best compatibility with Hyperdrive's caching", with postgres.js listed as also supported. The spec picks postgres.js. Worth a deliberate ADR sentence rather than an implicit choice, especially since the Cloudflare Drizzle + Hyperdrive example uses pg.
- Does the migration path work at all through Hyperdrive, or must drizzle-kit and src/migrate.ts always use the Neon direct URL? Hyperdrive's transaction-mode pooling, 60-second max statement duration and per-query connection assignment make it a poor fit for DDL and advisory-lock-based migration runners. The spec already implies a DATABASE_URL path; confirm that CI and the deploy workflow never route migrations through the Hyperdrive binding, and assert it in the migrator.
- Does Hyperdrive technically accept Neon's -pooler endpoint as an origin? Neon says do not do it and Cloudflare's guide says uncheck connection pooling, but neither states it is rejected. Not blocking, since the decision is to use the direct endpoint, but worth knowing whether a misconfigured staging config would fail loudly or silently degrade (SET would break, which would silently drop any statement_timeout).
