# Increments 9 to 11 facts (verified 2026-09-20)

Compiled from five parallel research passes. Every fact carries its source. "(unverified)" means the researcher could not confirm it from a primary source. "PLAN CONFLICT" means it contradicts `docs/plans/phase0-plan.md`.

## 1. Expo scaffold and monorepo

- expo latest is 57.0.24 (2026-09-18); sdk-57 equals latest. SDK 58 is only `next` 58.0.0-preview.3 (https://registry.npmjs.org/expo). Plan's `^57.0.23` resolves fine; tighten to `~57.0.24`.
- SDK 57 bundles react-native 0.86.3, react 19.2.3, expo-router ~57.0.22, expo-sqlite ~57.0.3, expo-widgets ~57.0.20, reanimated 4.5.1 (https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo/bundledNativeModules.json). `typescript` and `jest` are absent, so `expo install jest` pulls npm latest (30.5.2).
- Template devDeps are `typescript ~6.0.3`, `@types/react ~19.2.2` (https://raw.githubusercontent.com/expo/expo/sdk-57/templates/expo-template-default/package.json). PLAN CONFLICT (low): the plan's claim that "TS 7 breaks Expo 57's expectations" is **(unverified)** as stated. No Expo package declares a TypeScript requirement (https://raw.githubusercontent.com/expo/expo/sdk-57/packages/%40expo/cli/src/start/doctor/typescript/TypeScriptProjectPrerequisite.ts). Keep `~6.0.3` as policy, not requirement.
- Metro auto-configures for monorepos since SDK 52, not 54; `autolinkingModuleResolution` is automatic for monorepos from SDK 55 (https://raw.githubusercontent.com/expo/expo/sdk-57/docs/pages/guides/monorepos.mdx). PLAN CONFLICT (low) with section 3's "SDK 54+". Do not put `watchFolders` or `nodeModulesPaths` in metro.config.js; its whole body should be `getSentryExpoConfig(__dirname)` (https://docs.sentry.io/platforms/react-native/manual-setup/metro/).
- Isolated dependencies are supported from SDK 54 but Expo explicitly warns "some React Native libraries may cause build or resolution errors", with `nodeLinker: hoisted` as the escape hatch (same monorepos page). `experiments.onDemandFilesystem` is the first fallback to try (https://raw.githubusercontent.com/expo/expo/sdk-57/packages/%40expo/config-types/src/ExpoConfig.ts).
- pnpm 11 removed `onlyBuiltDependencies` in favour of `allowBuilds`, and `strictDepBuilds` defaults true, so the first install with build scripts hard-fails (https://pnpm.io/settings/build). Budget this in increment 1. pnpm latest 12.5.1.
- expo-router 57.0.22 has non-optional peers `@expo/metro-runtime` and `@expo/log-box` that the template does not install (https://registry.npmjs.org/expo-router/57.0.22). Add both explicitly.
- Typed routes are still beta and opt-in; `.expo/types` and `expo-env.d.ts` are gitignored and generated at dev-server start. CI typecheck on a clean checkout needs `npx expo customize tsconfig.json` first (https://raw.githubusercontent.com/expo/expo/sdk-57/docs/pages/router/reference/typed-routes.mdx).
- PLAN CONFLICT (medium): `enableSceneSupport` is an expo-build-properties plugin option, not an `ios.*` app-config key (https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-build-properties/src/pluginConfig.ts). Apps built with the iOS 27 SDK do not launch on iOS 27 without it (https://expo.dev/changelog/sdk-57).
- PLAN CONFLICT (low): the plan's file tree has no `_layout.tsx`. Expo Router needs `src/app/_layout.tsx` and `src/app/(app)/_layout.tsx` (https://raw.githubusercontent.com/expo/expo/sdk-57/docs/pages/router/advanced/authentication.mdx). `SQLiteProvider`'s memo compares `onInit` by reference, so it must be module-scope (https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-sqlite/src/hooks.tsx).
- `expo prebuild` cleans by default in SDK 57 (https://raw.githubusercontent.com/expo/expo/sdk-57/packages/%40expo/cli/src/prebuild/index.ts). Plan section 13's `--clean` is redundant, not wrong. Set `EXPO_NO_GIT_STATUS=1` in CI.
- jest-expo 57.0.5 is Jest 29 throughout and needs `@react-native/jest-preset@0.86.3` declared explicitly under pnpm isolated (https://registry.npmjs.org/jest-expo/57.0.5). Jest 30 compatibility is **(unverified)**. The preset already whitelists `.pnpm`. `@testing-library/react-native` 14 requires `test-renderer`, not the deprecated `react-test-renderer`.
- Vitest inside apps/mobile is **(unverified)**; Expo documents nothing. Keep mobile on jest-expo, push pure logic to packages/shared.
- `@sentry/react-native` 8.27.0's changelog carries an unreleased fix "Declare optional peer dependencies so imports resolve under strict and Plug'n'Play package managers" (https://raw.githubusercontent.com/getsentry/sentry-react-native/main/CHANGELOG.md). Expect resolution errors under pnpm isolated.
- `react-native-nitro-google-signin` 2.3.0 requires `react-native-nitro-modules` >=0.36.0, which no plan section names. SDK 57 compatibility is **(unverified)**: peers say only `expo >=49`, `react-native >=0.76`.

## 2. EAS, store and privacy

- Free EAS: 15 iOS and 15 Android builds/month, 1 concurrency, 45-minute timeout, no large workers. Starter $19 with $45 credit and a 2-hour timeout (https://expo.dev/pricing). The plan's 45-minute figure is confirmed; the claim that MapLibre plus Swift targets exceeds it is **(unverified)**. Per-build cost after credit is $2 medium iOS, $4 large (https://docs.expo.dev/billing/usage-based-pricing/), so nightly EAS iOS builds would exceed Starter credit. Keep native-smoke on GitHub runners.
- `autoIncrement` writes to EAS servers only when `cli.appVersionSource: "remote"`; with `"local"` CI must commit the bump back (https://docs.expo.dev/build-reference/app-versions/). The plan names autoIncrement but not appVersionSource.
- Runtime version policies today are `appVersion`, `nativeVersion`, `fingerprint`; no `sdkVersion` (https://docs.expo.dev/versions/latest/sdk/updates/). Use `fingerprint`: increment 11 adds four native surface families and only fingerprint notices.
- `--auto-submit` resolves the same-named submit profile and reaches TestFlight and the Play internal track only, never public release (https://docs.expo.dev/build/automate-submissions/). Needs `EXPO_TOKEN` in CI.
- PLAN CONFLICT (medium): "aggregated privacyManifests" is not automatic. `withPrivacyInfo` merges only what you declare, into the main app target only, and never scans node_modules (@expo/config-plugins 57.0.9 build/ios/PrivacyInfo.js; https://docs.expo.dev/guides/apple-privacy/). Aggregation of pod manifests is a separate expo-build-properties key `privacyManifestAggregationEnabled` whose default is **(unverified)**.
- Required reasons PlaneAhead needs: UserDefaults CA92.1 plus 1C8F.1 (App Group), FileTimestamp C617.1/0A2A.1/3B52.1, DiskSpace E174.1/85F4.1, SystemBootTime 35F9.1 (https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype; https://docs.sentry.io/platforms/react-native/data-management/apple-privacy-manifest/). Whether extensions need their own manifest is **(unverified)** for our targets but Apple says each executable using a required-reason API needs one.
- First-party analytics to our own Workers endpoint is not Tracking under Apple's definition, so no ATT prompt; the install id must still be declared as Identifiers > Device ID, Data Not Linked to You, purpose Analytics (https://developer.apple.com/app-store/app-privacy-details/). Google Play has no linked/not-linked concept; declare under "Device or other IDs" (https://support.google.com/googleplay/android-developer/answer/10787469).
- Magic links need `ios.associatedDomains` plus `android.intentFilters` with `autoVerify: true`, an AASA at `/.well-known/apple-app-site-association` and assetlinks.json carrying both Play upload and Play signing fingerprints (https://docs.expo.dev/linking/ios-universal-links/, https://docs.expo.dev/linking/android-app-links/). Neither is in the plan's app.config.ts list. Apple's CDN caches the AASA, so the path prefix is effectively immutable after first TestFlight.
- PLAN CONFLICT (medium, section 18): a Services ID is only needed for web sign-in (https://developer.apple.com/help/account/capabilities/configure-sign-in-with-apple-for-the-web/). Phase 0 needs the App ID capability and the .p8.
- Play personal accounts created after 2023-11-13 need 12 testers for 14 continuous days plus up to 7 days of review before production access (https://support.google.com/googleplay/android-developer/answer/14151465). Organization accounts avoid this. The plan defers Play Console to Phase 5; the account-type decision should move earlier.
- PLAN CONFLICT (low, section 18): a physical device is not required for the ActivityKit push-token loop; Simulator on Apple silicon works (https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications). Whether push-to-start tokens are issued in Simulator is **(unverified)**.
- Bundle identifier immutability after first store upload is **(unverified)** in any primary source, though correct in practice.

## 3. Auth client and native sign-in

- `expoClient({ scheme, storagePrefix, storage: SecureStore })` needs no `deleteItem`; storage is `Pick<typeof SecureStore, ...>` (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/expo/src/client-storage.ts). Cookies live in one JSON map at `${prefix}_cookie`; chunked above 1800 bytes.
- The client strips cookies and `expo-origin` only when `options.body?.idToken !== undefined` (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/expo/src/client.ts). Increment 5's `identityToken` naming is load-bearing; add a test asserting no `idToken` key.
- All five Expo peers are optional in metadata but `expo-constants` and `expo-linking` are static imports. Under pnpm isolated all five must be direct dependencies of apps/mobile.
- `GET /magic-link/verify` returns JSON plus `Set-Cookie` when no `callbackURL` is in the query, and only 302s otherwise; the token is consumed atomically (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/plugins/magic-link/index.ts). Calling it from inside the app carries the SecureStore anonymous cookie, which closes increment 5's known merge gap by design.
- The Expo server plugin appends the raw `set-cookie` value as a `?cookie=` query parameter on deep-link redirects (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/expo/src/index.ts), and no client code consumes it. A second reason to verify in-app. Record in the threat model.
- Apple's nonce is passed verbatim; the SHA-256 convention is ours, not Apple's (https://github.com/expo/expo/blob/sdk-57/packages/expo-apple-authentication/ios/AppleAuthenticationRequest.swift; https://developer.apple.com/documentation/authenticationservices/asauthorizationopenidrequest/nonce). Google's nonce is compared raw (https://developer.android.com/identity/sign-in/credential-manager-siwg-implementation). The asymmetry needs a code comment.
- PLAN CONFLICT (high, increment 5): Apple returns `email` and `fullName` only on the first authorization (https://github.com/expo/expo/blob/sdk-57/packages/expo-apple-authentication/src/AppleAuthentication.types.ts). Rejecting with 400 `email_required` breaks every returning user. Look up by `(providerId 'apple', accountId sub)` first.
- PLAN CONFLICT (medium, increment 9 acceptance): `getCredentialStateAsync` always throws on the iOS Simulator, and the Pixel AVD needs a Google APIs image plus the full `checkPlayServices` → `signIn` → `createAccount` → `presentExplicitSignIn` ladder on a fresh emulator (https://github.com/react-native-nitro-google-sign-in/google-signin/blob/main/README.md).
- Trap: the nitro library's docs say the nonce rotates automatically; the source shows a configured nonce is sticky for the process lifetime. Call `configure()` before every `signIn()`.
- Guideline 4.8 makes Sign in with Apple mandatory once native Google ships (https://developer.apple.com/app-store/review/guidelines/).
- Expo SDK 57's winter runtime installs no global `crypto` (https://github.com/expo/expo/blob/sdk-57/packages/expo/src/winter/runtime.native.ts), so `uuidv7()` from packages/shared will throw on Hermes. Add `expo-standard-web-crypto` and call `polyfillWebCrypto()` as the first statement of the entry.
- Numeric Sign in with Apple HIG rules are **(unverified)**; the page is client-rendered. Moot if the native `AppleAuthenticationButton` is used.

## 4. Observability and state

- PLAN CONFLICT (medium): SDK 57 pins `@sentry/react-native ~7.11.0` (https://api.expo.dev/v2/sdks/57.0.0/native-modules), while npm latest is 8.27.0. v7-to-v8 is a native-floor bump with no `Sentry.init` API change (https://docs.sentry.io/platforms/react-native/guides/expo/migration/v7-to-v8/). Which 8.x first supports SDK 57 is **(unverified)**; issue 6384 is closed without an extractable version.
- PLAN CONFLICT (medium): Sentry's own Expo quickstart sets `sendDefaultPii: true` plus mobile replay (https://docs.sentry.io/platforms/react-native/manual-setup/expo/). Anyone running the wizard gets the opposite of plan sections 3 and 10.
- With PII off the SDK still sends full outgoing URLs, Referer and query strings, and console logs as breadcrumbs (https://docs.sentry.io/platforms/react-native/data-management/data-collected/). The magic-link URL is the concrete exposure; `beforeBreadcrumb` and `beforeSend` scrubbing are mandatory, not optional.
- EAS Update bundles do not get automatic source maps; `npx sentry-expo-upload-sourcemaps dist` is a separate CI step (https://docs.expo.dev/guides/using-sentry/).
- TanStack Query documents a verbatim `expo-network` recipe for `onlineManager`, removing the need for `@react-native-community/netinfo` (https://tanstack.com/query/latest/docs/framework/react/react-native). It documents no persistence requirement, supporting the plan's decision to skip `persistQueryClient`.
- PLAN-RELEVANT: `credentials: 'include'` will not work with the Hono client, because the session cookie lives in SecureStore, not RN's cookie jar. Use `hc<AppType>(base, { headers: async () => ({ Cookie: await authClient.getCookie() }), init: { credentials: 'omit' } })` (https://better-auth.com/docs/integrations/expo; https://raw.githubusercontent.com/honojs/hono/main/src/client/types.ts). Whether the async headers function is evaluated per request is **(unverified)**.
- `expo-sqlite/kv-store` exposes synchronous `getItemSync`/`setItemSync`, which gives zustand `persist` synchronous hydration and removes the first-render gate (https://docs.expo.dev/versions/latest/sdk/sqlite/). It is a separate database file, so it is fine for preferences and disqualified for the sync cursor (already in increment 8 facts).
- `getDevicePushTokenAsync()` returns the raw APNs/FCM token with no Expo service involvement (https://docs.expo.dev/push-notifications/sending-notifications-custom/). Whether an Android FCM token needs `google-services.json` in a dev build is **(unverified)**.
- MapLibre 11.4.0 is New Architecture only, peers `expo >=54`, and is absent from Expo's bundled-modules list, so `expo install` gives no compatibility guarantee (https://registry.npmjs.org/@maplibre/maplibre-react-native/latest; https://github.com/maplibre/maplibre-react-native/releases/tag/v11.0.0).

## 5. Native surfaces (increment 11)

- expo-widgets 57.0.20 is stable since SDK 56, iOS-documented, not in Expo Go (https://docs.expo.dev/versions/latest/sdk/widgets/; https://expo.dev/blog/ios-widgets-and-live-activities-in-expo).
- PLAN CONFLICT (low): a Live Activity created with `createLiveActivity` must **not** have a `widgets[]` entry; an entry without `supportedFamilies` generates an invalid target that fails to build (https://raw.githubusercontent.com/expo/expo/main/docs/pages/versions/unversioned/sdk/widgets.mdx). Only the placeholder widget gets one.
- Widget components use the `'widget'` directive, render only `@expo/ui/swift-ui`, and cannot use hooks, state, imports, or anything declared outside the function body.
- The `bannerSmall` Live Activity region already renders on a paired Apple Watch with no watchOS target, weakening the case for the apple-targets watch shell.
- Apple caps Live Activity static plus dynamic data at 4 KB combined and active duration at 8 hours, 12 hours on the Lock Screen (https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities). A long-haul flight exceeds this; the plan has no answer.
- PLAN CONFLICT (medium): push tokens are per Live Activity and rotate during the activity, with a server obligation to invalidate the old one. Increment 5's `push_tokens` keyed on `(user_id, install_id)` with four fixed kinds cannot represent N rotating tokens, yet plan section 11 says listeners post to `/v1/devices`.
- PLAN CONFLICT (high, deferred): expo-widgets sets `aps-environment` to the literal `'development'` unconditionally, and `ios.entitlements` is applied before all plugins (https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-widgets/plugin/src/ios/withPushNotifications.ts). A production Live Activity token would be minted against sandbox APNs. Needs a local plugin ordered last.
- expo-widgets defaults the App Group to `group.<bundleIdentifier>`, so three APP_VARIANT ids yield three groups, each needing Apple registration, or pass an explicit `groupIdentifier`. apple-targets mirrors `ios.entitlements` at config-evaluation time, before expo-widgets' entitlement mod runs, so the group must be declared explicitly in app.config.ts as well.
- PLAN CONFLICT (medium): expo-widgets 57.0.20 already ships an Android Glance implementation behind undocumented `enableAndroid: true`, and SDK 58 promotes it to a supported JS/Hermes feature (https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-widgets/plugin/src/withWidgets.ts; https://expo.dev/changelog/sdk-58-beta). The hand-written Kotlin Glance widget in `modules/android-surfaces` is likely redundant.
- expo/expo#49752 (open): the widget JS bundle fails to resolve hoisted packages when expo-widgets is nested in a workspace, exactly PlaneAhead's shape. Reproduction under pnpm isolated is **(unverified)**.
- `@bacons/apple-targets` 5.0.0 depends on `@expo/prebuild-config ~55.0.6` against SDK 57's 57.0.16, and its README claims only Xcode 16 and Expo SDK 53+. Xcode 27 support is **(unverified)**. Three watch-target defects are open (207, 171, 148), plus #194, a dyld failure that builds clean and dies at launch.
- Target names and EAS credential entries do not collide (`ExpoWidgetsTarget` versus directory name). The real hazard is two pbxproj parsers (`xcode` versus `@bacons/xcode` 1.0.0-alpha.32) mutating one project, with no public report either way: **(unverified)**.
- EAS SDK 57 images are `macos-tahoe-26.5-xcode-26.6` and `ubuntu-26.04-jdk-17-ndk-r27b-sdk-57` (https://docs.expo.dev/build-reference/infrastructure/), so a nightly on Xcode 27 does not mirror production. SDK 57 has an open Xcode 27 defect of its own (expo/expo#47537).
- Android Live Updates need API 36, `POST_PROMOTED_NOTIFICATIONS` and `setRequestPromotedOngoing` (https://developer.android.com/develop/ui/views/notifications/live-update). The androidx.core version that first carried it is **(unverified)**. Expo has no Wear OS support of any kind; `plugins/withWearApp.ts` is written from scratch.

## Decisions the orchestrator must take

1. **Sentry version.** Pin `~7.11.0` (Expo's own pin, expo-doctor green) rather than 8.27.0; trade-off is running a version behind while 8.x has an unreleased strict-package-manager fix we would want anyway.
2. **Sentry privacy config.** Write an explicit test asserting `sendDefaultPii: false`, no replay, plus URL and query scrubbing in `beforeSend`/`beforeBreadcrumb`; trade-off is more config surface than the plan's one-line "PII off".
3. **Magic-link verification path.** Verify in-app via `authClient.magicLink.verify` with no `callbackURL`; trade-off is owning the deep-link parse instead of inheriting Better Auth's redirect, in exchange for the anonymous merge working and no cookie in a URL.
4. **Apple email rule.** Change increment 5 to look up by `sub` and demand email only when no account row exists; trade-off is a user row without an email for managed Apple IDs.
5. **Scene support placement.** Move `enableSceneSupport: true` into expo-build-properties from day one; trade-off is nothing, and the alternative is an app that will not launch on iOS 27.
6. **Runtime version policy.** Use `fingerprint`, not `appVersion`; trade-off is more frequent rebuilds in exchange for updates never reaching a build with a different native surface set.
7. **Universal links in increment 9.** Add `associatedDomains`, `intentFilters` and both well-known files now, with a broad `/auth/*` prefix; trade-off is committing to a path prefix permanently because Apple's CDN caches the AASA.
8. **App Group ownership.** Declare the group explicitly in app.config.ts and pass the same string to expo-widgets' `groupIdentifier`; trade-off is one hand-maintained string versus three per-variant groups to register with Apple.
9. **aps-environment plugin slot.** Reserve a local plugin ordered last in increment 9, implement in increment 11; trade-off is a stub plugin now versus discovering sandbox push tokens in production.
10. **Live Activity token schema.** Either add a `live_activities` table keyed on activityId or scope Phase 0 to push-to-start only; trade-off is schema work now versus a listener that logs and discards.
11. **Android widget ownership.** Drop the hand-written Glance widget, keep `android-surfaces` for the ongoing-notification stub only; trade-off is depending on SDK 58 for Android widgets rather than owning Kotlin.
12. **Watch shell expectation.** Assume ADR 0008 fires and watch moves to Phase 2; trade-off is shipping less in Phase 0 against burning increment 11 on an alpha pbxproj parser with three open watch defects.
13. **Native-smoke host and depth.** Run on `macos-26` with Xcode 26.6 to mirror EAS, add Xcode 27 as continue-on-error, and install-and-launch on a simulator rather than compile only; trade-off is a slower nightly that actually catches dyld failures.
14. **Isolated linker proof.** Prove `expo prebuild` plus both compiles under `nodeLinker: isolated` in increment 1; trade-off is front-loading a day against invalidating a section 3 decision during increment 11.
15. **React Compiler.** Turn `experiments.reactCompiler` off for Phase 0; trade-off is losing auto-memoization while the useLiveQuery list is unprofiled.
16. **Play account type.** Register Play as an Organization before Phase 5; trade-off is D-U-N-S paperwork now versus a 21-day gate on Android launch.

## Appendix: open questions per research topic

### expo-scaffold (55 facts, 1 unverified)

- What is the default value of `privacyManifestAggregationEnabled` in expo-build-properties 57.0.21? The source doc comment has no @default tag and the docs page was not retrievable. Set it explicitly to true in app.config.ts rather than relying on a default, and confirm the aggregated PrivacyInfo.xcprivacy exists in the archive during the increment 11 nightly.
- Does jest-expo 57.0.5 run on Jest 30.5.2? Its own dependency tree is entirely Jest 29 and the CHANGELOG never mentions Jest 30. Until someone runs it, pin jest 29.7.0. If Jest 30 does work, the toolchain-guard job should be relaxed, because 29.7.0 is a 2023 release with no further security patches.
- Does `expo/tsconfig.base`'s `noEmit: true` plus `customConditions: ["react-native"]` survive TypeScript project references from apps/mobile into packages/shared? The plan routes shared types through project references, but noEmit blocks declaration emit and the react-native condition changes resolution. Prove this in increment 1 with a trivial shared type, not in increment 9.
- Which exact expo 57.x patch fixed the Hermes V1 memory regression inherited from SDK 56? The changelog names the problem but not the fixing version. 57.0.24 is the safe pin, but the answer decides whether a Renovate downgrade or a lockfile rollback is ever safe.
- Is react-native-nitro-google-signin 2.3.0 actually compatible with Expo SDK 57 and RN 0.86 New Architecture? Its peers only say `react-native >=0.76` and `expo >=49`, with no SDK 57 statement anywhere in the repo or npm metadata. Increment 5 already committed to this library for the native Google path, so a prebuild plus compile smoke test belongs in increment 1, not increment 9.

### auth-client-and-native-signin (48 facts, 1 unverified)

- Does the in-app magic-link verify actually receive the universal link, or does the email client intercept it? Apple Mail, Gmail and Outlook on iOS handle universal links differently, and Gmail on Android has historically opened links in its own webview rather than honouring the App Link. If the link lands in a webview, the app never sees it and the design silently degrades to a browser flow with no anonymous merge. This needs a real-device check across at least Apple Mail, Gmail iOS, Gmail Android and Outlook iOS before increment 9 closes, and it is the only remaining device-only risk in this topic.
- Do email clients or security scanners prefetch the magic link and burn the single-use token before the user taps? The token is consumed atomically on the first verify call. Outlook Safe Links and several corporate gateways do exactly this. If it happens, the design needs a two-step confirm page rather than a direct token in the URL, which is a meaningful change to the increment 5 sender and the increment 9 screen.
- Which universal-link path prefix goes in apple-app-site-association? iOS caches the AASA at install and App Store update, so narrowing the path list later requires a full store release. Decide the permanent prefix (suggest /auth/*) before the first TestFlight build, not at increment 9.
- Is `setSessionCookie` plus `handleOAuthUserInfo` (the two subpath exports increment 5's plugin depends on) stable enough to build two production sign-in paths on? Still not answerable from published docs; the 1.7.5 exact pin remains the only mitigation, and the mobile side inherits the risk.
- What exactly does the Expo client store when the session_data cookie chunks? getChunkedCookie exists server-side and the client chunks at 1800 bytes, but the multi-chunk replay path was not traced end to end in either research pass. If a PlaneAhead session_data cookie crosses 1800 bytes the native session cache could degrade silently. Measure the encoded cookie size for a real user in increment 9 and assert it.
- Should the app call getCredentialStateAsync on foreground to detect an Apple credential revoked from Settings? It cannot be tested on the simulator, and increment 8 already handles server-side revoke for deletion. If the answer is yes, it needs a device test lane that the plan's nightly native-smoke job does not currently provide.
- Does react-native-nitro-google-signin's iOS Podfile patch survive a prebuild that also contains the expo-widgets extension and the @bacons/apple-targets watch target? Plan section 11 already calls that coexistence an explicit acceptance test for increment 11; this adds a third patcher to the same Podfile. Worth testing in increment 9 rather than discovering it in increment 11.
- Do we pin react-native-nitro-google-signin at 2.3.0 exact and accept manual upgrades? It shipped 25 releases and two breaking majors in under four months with 47 stars. The server contract is ours and stable, but the client call site will move. Decide the Renovate policy now (suggest: no auto-merge, quarterly review) so it does not auto-bump into a broken build.
- Which nonce length do we standardise on? Apple warns the accepted nonce size may depend on the technology used and may cause a request error, and Google's sample uses 32 random bytes.
