# Increment 5 facts (verified 2026-09-20)

Every fact below was checked against a primary source on 2026-09-20. Items no researcher could confirm are tagged **(unverified)**. Facts contradicting `docs/increments/05-auth.md` are marked **SPEC CONFLICT**. Better Auth schema facts are not repeated here; see `03-db-schema.facts.md` section 1.

## 1. Better Auth config on Workers

- `betterAuth()` does no network or DB I/O at construction; `init` is eager, `handler()` awaits it on first request. Per-request `createAuth(env, db)` is CPU only and correct. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/auth/base.ts)
- `better-auth/minimal` is a second entry point that skips Kysely and is intended for `drizzleAdapter` users. Bundle saving is not measured **(unverified)**. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/auth/minimal.ts)
- The Drizzle schema check is an in-memory diff over the object you pass, zero SQL. Pass the 5-key subset, not 61 tables. `advanced.database.validateSchema: false` removes it. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/drizzle-adapter/src/schema-check.ts)
- **SPEC CONFLICT, high.** `isProduction` is `env.NODE_ENV === "production"`, and Workers never set `NODE_ENV`. So `rateLimit.enabled` resolves **false** and rate limiting is silently off, and `validateSecret` does not throw on a missing `BETTER_AUTH_SECRET`, falling back to a hardcoded public `DEFAULT_SECRET` that keys session signing and OAuth token encryption. Set `rateLimit.enabled: true` and assert the secret yourself. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/context/create-context.ts, .../packages/core/src/env/env-impl.ts)
- Same root cause: `expo()` only injects `trustedOrigins: ["exp://"]` when `NODE_ENV === "development"`, so `wrangler dev` rejects Expo Go unless you list it yourself. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/expo/src/index.ts)
- **SPEC CONFLICT.** The `cf-connecting-ip` option is `advanced.ipAddress.ipAddressHeaders`, not part of `rateLimit`. Default is `["x-forwarded-for"]`, and a comma chain resolves to `null` without `trustedProxies`. With no IP, the limiter fails closed onto one shared `"no-trusted-ip"` bucket per path, which a client can trigger deliberately. Set `advanced: { ipAddress: { ipAddressHeaders: ['cf-connecting-ip'] } }`. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/core/src/utils/ip.ts)
- Cloudflare sets `CF-Connecting-IP` at the edge, always one IP, and recommends it over `X-Forwarded-For`. (https://developers.cloudflare.com/fundamentals/reference/http-headers/)
- Resolved rateLimit defaults: window 10, max 100, storage `memory`. The docs page says 60 s; the source says 10. Built-in special rules already give `/sign-in*`, `/sign-up*` window 10 / max 3, so the spec's `customRules` may be a no-op unless tighter. `customRules` keys are `basePath`-relative (`/sign-in/magic-link`) and win over plugin rules. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/api/rate-limiter/index.ts)
- `storage: 'database'` does a SELECT plus a guarded `incrementOne` UPDATE or INSERT on every auth request, plus a periodic `deleteMany` sweep. It is race-safe but depends on `rate_limits.lastRequest` surviving postgres.js to Drizzle `bigint({ mode: 'number' })`, still **(unverified)** from increment 3. `memory` is a per-isolate Map and enforces nothing. `secondary-storage` requires an atomic `SecondaryStorage.increment`, which KV cannot give, so it implies a Durable Object. (same source)
- The Hono mount is `app.all('/api/auth/*', c => auth.handler(c.req.raw))` and Workers need `nodejs_compat` or `nodejs_als` for AsyncLocalStorage. **SPEC CONFLICT (minor):** the spec's `app.on(['GET','POST'], ...)` covers every 1.7.5 endpoint but drops OPTIONS preflight; no CORS middleware is specified. (https://github.com/better-auth/better-auth/blob/v1.7.5/docs/content/docs/integrations/hono.mdx)
- There is no Cloudflare Workers integration page in the 1.7.5 docs; `/docs/integrations/cloudflare` 404s. (https://www.better-auth.com/docs/integrations/cloudflare)
- `session.cookieCache.strategy: 'compact'` and `maxAge: 300` are already the 1.7.5 defaults; only `enabled: true` is load bearing. Cached sessions skip the DB read, so revocation lags by up to `maxAge`. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/core/src/types/init-options.ts)
- `AnonymousOptions` is exactly `emailDomainName`, `onLinkAccount`, `disableDeleteAnonymousUser`, `generateName`, `generateRandomEmail`, `schema`. A second anonymous sign-in with a live session returns 400. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/plugins/anonymous/types.ts)
- `magicLink` options: `sendMagicLink(data, ctx?)` where the second argument is the endpoint context, not a Request; `storeToken: 'hashed'` and `expiresIn: 600` are valid. `POST /sign-in/magic-link` always writes a verification row and always calls `sendMagicLink`, so the per-email cap must run before it (Hono middleware) or inside the sender. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/plugins/magic-link/index.ts)
- **SPEC CONFLICT.** There is no Expo session header. The Expo client stores the cookie in SecureStore and replays it as `Cookie` with `credentials: 'omit'`; `expo-origin` is an origin override only. The middleware collapses to `auth.api.getSession({ headers: c.req.raw.headers })`. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/expo/src/client.ts)
- `trustedOrigins` must include `planeahead://` or the deep-link redirect carries no session cookie and fails silently. `expo()` also registers `GET /expo-authorization-proxy`, whose source carries a FIXME about redirects to unrelated https hosts. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/expo/src/routes.ts)
- `account.encryptOAuthTokens` uses XChaCha20-Poly1305 via `@noble/ciphers`, not the AES-256-GCM its own JSDoc claims, keyed on SHA-256 of the secret, with its own `$ba$<version>$` envelope rotated via `BETTER_AUTH_SECRETS`. That is a second, independent key scheme alongside `TOKEN_KEK_V{n}`. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/crypto/index.ts)

## 2. Session creation and the anonymous merge

- `internalAdapter.createSession(userId, dontRememberMe?, override?, overrideAll?, storageOptions?)` takes **no ctx**. Passing `ctx` second coerces to truthy `dontRememberMe` and silently creates a 1-day session. It reads headers from AsyncLocalStorage, so outside `runWithEndpointContext` the `ip_address` and `user_agent` are empty strings. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/db/internal-adapter.ts)
- The cookie value is not the raw token: better-call 1.4.0 signs `encodeURIComponent(token + "." + btoa(HMAC-SHA256))` using standard base64. Do not hand-roll it. Cookie name is `better-auth.session_token`, prefixed `__Secure-` when secure, so it differs between `wrangler dev` (http) and deployed https. (better-call@1.4.0 `dist/crypto.mjs`; https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/cookies/index.ts)
- `handleOAuthUserInfo(ctx, {...})` is exported from `better-auth/oauth2` and does find-or-create user, link-or-create account inside `runWithTransaction`, applies the linking policy, and creates the session. Pair with `setSessionCookie(ctx, data)` from `better-auth/cookies`, which also sets `ctx.context.newSession`, the signal the anonymous hook needs. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/oauth2/link-account.ts)
- `POST /sign-in/social` with `idToken` accepts `refreshToken` but never persists it; it does write the raw `idToken` plaintext into `accounts.id_token`. It throws `USER_EMAIL_NOT_FOUND` when the profile has no email. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/api/routes/sign-in.ts)
- **SPEC CONFLICT, high.** The anonymous link after-hook matches only paths starting with `/sign-in`, `/sign-up`, `/callback`, `/magic-link/verify`, `/email-otp/verify-email`, `/one-tap/callback`, `/passkey/verify-authentication`, `/phone-number/verify`, `/verify-email`. The spec's `/api/auth/apple/native` has path `/apple/native` and matches none, so `onLinkAccount` never fires for Apple. Register at `/sign-in/apple-native`. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/plugins/anonymous/index.ts)
- **SPEC CONFLICT, high.** The Expo client omits the stored cookie for any request whose body has an `idToken` key (except `/link-social`), so native Google ID-token sign-in resolves no anonymous session and `onLinkAccount` never fires. The OAuth-state fallback only covers `/sign-in/social` redirects. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/expo/src/client.ts)
- `onLinkAccount` is an after-hook, **not** in a transaction: the new user, session and Set-Cookie are already committed when it runs. A throw leaves a half-finished upgrade. The merge must be idempotent and replayable, and the callback receives `{ anonymousUser, newUser, ctx }` (the spec drops `ctx`). (same anonymous source)
- `auth.api.*` calls skip `originCheckMiddleware`, which is registered only on the router path. Custom routes do their own origin checks. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/api/index.ts)
- For increment 8: `deleteUser` runs `beforeDelete`, then cascades accounts, so Apple revoke must be in `beforeDelete`. Default `freshAge` is 1 day; with 30-day sessions and no passwords, the plain delete path throws `SESSION_EXPIRED` for essentially every real user. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/better-auth/src/api/routes/update-user.ts)
- Better Auth 1.7.5 has no Apple revocation anywhere (verified by absence over the full v1.7.5 tree). (https://api.github.com/repos/better-auth/better-auth/git/trees/v1.7.5?recursive=1)
- Whether `ctx.context.newSession` and the anonymous hook behave identically when a plugin endpoint is called via `auth.api.*` rather than HTTP is **(unverified)**; source reading says yes, it was not executed.

## 3. Apple and Google tokens

- Apple identity token claims: `iss`, `sub`, `aud`, `iat`, `exp`, `nonce`, `nonce_supported`, `email`, `email_verified`, `is_private_email`, `real_user_status`, `transfer_sub`, `org_id`, `scopes`. `email_verified` and `is_private_email` may arrive as booleans **or** the strings `"true"`/`"false"`. `email` can be absent for Apple School/Business accounts. (https://developer.apple.com/documentation/signinwithapplejs/authorizationi/id_token)
- **SPEC CONFLICT.** Apple identity tokens are **RS256**; the live JWKS at https://appleid.apple.com/auth/keys served 3 RSA/RS256 keys on 2026-09-20, although Apple's prose still says "JWS E256". Pin `algorithms: ['RS256']`. ES256 applies only to the client secret you mint. (https://developer.apple.com/documentation/signinwithapple/verifying-a-user)
- Apple passes the nonce through verbatim; SHA-256 hashing is a client convention, and `expo-apple-authentication` assigns `request.nonce = options.nonce` with no hashing. The client must send `sha256hex(rawNonce)` to Apple and `rawNonce` to the API. (https://developer.apple.com/documentation/authenticationservices/asauthorizationopenidrequest/nonce)
- `POST https://appleid.apple.com/auth/token`, form-encoded, requires `client_id`, `client_secret`, `code`, `grant_type=authorization_code`; omit `redirect_uri` for a native flow. The code is single-use, valid 5 minutes, and `refresh_token` is returned only on this initial exchange. (https://developer.apple.com/documentation/signinwithapplerestapi/generate-and-validate-tokens)
- Client secret: ES256 JWT, header `{alg: ES256, kid}`, payload `{iss: teamId, iat, exp, aud: https://appleid.apple.com, sub: clientId}`, `exp` at most 15777000 s out. The spec's 1 h isolate cache is safely inside that. (https://developer.apple.com/documentation/accountorganizationaldatasharing/creating-a-client-secret)
- `POST https://appleid.apple.com/auth/revoke` takes `client_id`, `client_secret`, `token`, optional `token_type_hint`. `client_id` must match the authorization request, so the bundle id for native. The enumeration of 400 error codes is **(unverified)**. (https://developer.apple.com/documentation/signinwithapplerestapi/revoke-tokens)
- **SPEC CONFLICT.** Apple's full name is not in the identity token; it arrives once, out of band, and Apple requires it be validated and sanitised before storage. Treat the `fullName` body field as attacker-controlled. (https://developer.apple.com/documentation/signinwithapple/receiving-a-users-identity-token)
- **SPEC CONFLICT.** Private relay addresses use three domains: `@privaterelay.appleid.com`, `@icloud.com` and `@private.icloud.com`, with new addresses moving to `private.icloud.com` "later this year" (no date, **unverified**). Branch on the `is_private_email` claim, never the domain. Per-address limit is 100 emails/day. (https://developer.apple.com/documentation/signinwithapple/communicating-using-the-private-email-relay-service, https://developer.apple.com/news/?id=1ptvdtcm)
- **SPEC GAP, blocking.** Outbound domains must be registered under Certificates, Identifiers & Profiles > Services > Sign in with Apple for Email Communication, or mail to relay addresses bounces. Apple SPF-checks the **envelope sender** domain, which under Resend defaults to `send.planeahead.app`, so both `planeahead.app` and `send.planeahead.app` must be registered. Limits: 32 sources (individual), 100 (organization). (https://developer.apple.com/help/account/capabilities/configure-private-email-relay-service/, https://resend.com/docs/knowledge-base/sending-apple-private-relay)
- Google: `iss` is `https://accounts.google.com` or `accounts.google.com`; `aud` must be one of your client ids, and Google's own sample shows an array for multi-client backends, so the spec's three client ids work. JWKS is `https://www.googleapis.com/oauth2/v3/certs`, RS256 only. (https://developers.google.com/identity/sign-in/ios/backend-auth, https://accounts.google.com/.well-known/openid-configuration)
- **SPEC CONFLICT, high.** `idToken.nonce` is optional and `verifyProviderIdToken` skips the nonce check entirely when absent, so "verifies nonce" cannot be met by configuration. Enforce with a before-hook on `/sign-in/social` rejecting `idToken` without `nonce`. Google's comparison is exact; Apple's is `exact-or-sha256` (lowercase hex). (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/core/src/oauth2/verify-id-token.ts)
- **SPEC CONFLICT.** Better Auth hardcodes Google's JWKS URL with no override, so "against a test JWKS" is impossible through the stock provider. Use `socialProviders.google.verifyIdToken`, which is checked first. Both built-in JWKS fetchers also refetch on every verification with no cache. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/core/src/social-providers/google.ts)
- Better Auth's `apple` provider already verifies native tokens via `appBundleIdentifier` or `audience`, `maxTokenAge` 1 h, `nonceComparison: 'exact-or-sha256'`. The spec's "web only" framing understates this. (https://github.com/better-auth/better-auth/blob/v1.7.5/packages/core/src/social-providers/apple.ts)
- **SPEC CONFLICT (client).** Nonce support in `@react-native-google-signin/google-signin` exists only in the paid Universal Sign In module; the free Original module's `configure()` has no `nonce` and rides the deprecated legacy Android SDK. `react-native-nitro-google-signin` 2.3.0 is MIT, uses Android Credential Manager, and takes an explicit nonce (it auto-generates one the server never sees if you omit it). Expo's current guide lists only these two modules, not `expo-auth-session`. (https://docs.expo.dev/guides/google-authentication/, https://react-native-google-signin.github.io/docs/original)
- Whether GoogleSignIn-iOS 9.0.0+ reliably surfaces the custom nonce as the `nonce` claim is **(unverified)**; confirm on device.
- `jose` 6.2.12 is MIT, zero-dependency, documents Cloudflare Workers support. `createRemoteJWKSet` performs no I/O at construction (safe at module scope), caches 10 min with a 30 s cooldown, and jose explicitly says not to use the external `jwksCache` on runtimes that keep in-memory state. Do not put JWKS in KV. (https://github.com/panva/jose/blob/v6.2.12/docs/jwks/remote/functions/createRemoteJWKSet.md)

## 4. WebCrypto envelope on Workers

- AES-KW supports `wrapKey`/`unwrapKey`/`importKey` only; workerd explicitly rejects `encrypt`/`decrypt` usages and rejects raw keys that are not 128/192/256 bits. (https://developers.cloudflare.com/workers/runtime-apis/web-crypto/, https://github.com/cloudflare/workerd/blob/main/src/workerd/api/crypto/aes.c%2B%2B)
- **SPEC CONFLICT (runtime trap).** `wrapKey` exports the target key first, so the per-user DEK must be imported `extractable: true` on the write path or it throws `DOMInvalidAccessError`. `unwrapKey` should produce `extractable: false` on the read path. The KEK stays non-extractable. (https://github.com/cloudflare/workerd/blob/main/src/workerd/api/crypto/crypto.c%2B%2B)
- AES-KW input must be a multiple of 8 bytes, minimum 16, and adds exactly 8, so a 32-byte DEK wraps to exactly 40 bytes. Wrap format must be `raw`; `jwk` JSON is not guaranteed to be a multiple of 8 (that conclusion is inference from the two verified constraints, **unverified** as a documented rule). (same aes.c++ source)
- AES-GCM `tagLength` defaults to 128 and the tag is appended, so stored layout is `iv(12) || ct(n) || tag(16)`. workerd requires a non-empty IV but does **not** enforce 12 bytes, so `envelope.ts` must enforce it on both paths. AAD is supported and takes a BufferSource. (same source)
- SubtleCrypto acquires no IoContext, so a `CryptoKey` is not an I/O object and can be memoised per isolate. `crypto.getRandomValues` and `randomUUID` **do** acquire one and throw at global scope, so DEK and IV generation must happen inside a handler. (https://github.com/cloudflare/workerd/blob/main/src/workerd/api/crypto/crypto.c%2B%2B)
- Module-scope state is per isolate and shared across users, so memoise the KEK and never the DEK. (https://developers.cloudflare.com/workers/best-practices/workers-best-practices/)
- `crypto.subtle.timingSafeEqual` exists but **throws** `TypeError` on unequal byte lengths rather than returning false, so length-check first or a malformed token becomes a 500. (https://developers.cloudflare.com/workers/runtime-apis/web-crypto/)
- `atob` rejects the base64url alphabet, so store `TOKEN_KEK_V{n}` as standard padded base64 or decode with `Buffer.from` under `nodejs_compat`. Secrets are capped at 5 KB each, 128 vars per paid Worker, so multiple KEK versions are free. (https://developers.cloudflare.com/workers/runtime-apis/web-standards/, https://developers.cloudflare.com/workers/platform/limits/)
- Whether the docs page's claim that compatibility dates from 2026-08-04 enable `nodejs_compat` by default is accurate is **(unverified)**; it was read from a page summary. Re-read before pinning `compatibility_date`.
- Whether `@cloudflare/vitest-pool-workers` enforces the global-scope entropy restriction is **(unverified)** (open workers-sdk issue 12886), so a module-scope `getRandomValues` bug could pass CI and fail on deploy.
- Whether Workers `importKey` accepts `pkcs8` for ECDSA P-256 specifically is **(unverified)**; the supported-algorithms table does not enumerate curves or formats. Settle with a one-line test before writing `apple-client-secret.ts`.
- The NIST 2^32 bound on random 96-bit IVs per key is **(unverified, not fetched)** and is irrelevant under per-user DEKs. The spec's "IV never repeats across 10k calls" test is an RNG sanity check, not a security bound.

## 5. Mail, limits and Expo client

- Resend send is `POST https://api.resend.com/emails`, Bearer key, required `from`/`to`/`subject`, success body is exactly `{"id": "<uuid>"}`. `Idempotency-Key` is supported, max 256 chars, retained 24 h, and a reused key with a different payload returns 409. Whether at least one of `html`/`text` is required is **(unverified)**. (https://resend.com/docs/api-reference/emails/send-email, https://resend.com/docs/dashboard/emails/idempotency-keys)
- Resend errors worth branching on: 403 `validation_error` for an unverified domain or pre-verification sends, 401 `missing_api_key`, and three distinct 429s: `rate_limit_exceeded` (retryable, honour `retry-after`), `daily_quota_exceeded` and `monthly_quota_exceeded` (not retryable). (https://resend.com/docs/api-reference/errors)
- Free tier is 3,000/month and 100 per **UTC calendar day**; API limit is 10 rps per team. At the spec's 3/hour and 10/day per-email caps that is roughly 10 distinct sign-in users per day. (https://resend.com/docs/knowledge-base/account-quotas-and-limits, https://resend.com/docs/api-reference/rate-limit)
- Resend's Return-Path defaults to `send.<domain>` and is configurable. Exact DNS record values are generated per domain in the dashboard and are **(unverified)** from docs. (https://resend.com/changelog/custom-return-path, https://resend.com/docs/add-a-domain)
- Cloudflare Email Sending is Beta, **Workers Paid only**, requires the domain to be on Cloudflare DNS, gives 3,000/month then $0.35/1,000, and publishes **no numeric starting daily quota** ("a conservative daily quota" that scales) **(unverified)**. Arbitrary recipients are allowed only after onboarding a sending domain. Its bounce subdomain is `cf-bounce.<domain>`, which would need its own Apple registration. Keeping it flagged off is correct. (https://developers.cloudflare.com/email-service/platform/limits/, .../pricing/, .../get-started/send-emails/)
- The Workers rate limit binding uses top-level `ratelimits` with `simple: { limit, period }` where `period` must be exactly 10 or 60 seconds, needs Wrangler 4.36.0+, and is **per Cloudflare location**, eventually consistent, and explicitly "not an accurate accounting system". `USER_RL` is an abuse damper; the 3/hour and 10/day caps stay in `usage_counters`. (https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)
- **Premise correction.** Expo SecureStore has no documented 2048-byte cap; Expo calls it historical iOS behaviour and enforces nothing. It is moot: `@better-auth/expo` 1.7.5 already chunks at 1800 UTF-8 bytes across up to 100 keys and normalises colons out of key names, so roughly 180 KB per logical value. No chunking work needed. (https://docs.expo.dev/versions/v57.0.0/sdk/securestore/, https://github.com/better-auth/better-auth/blob/v1.7.5/packages/expo/src/client-storage.ts)
- SecureStore `keychainAccessible` defaults to `WHEN_UNLOCKED`, so the session cookie is unreadable while the device is locked. Relevant to increment 7 background work.
- **SPEC CONFLICT.** "Nothing else" for deps is wrong. `@better-auth/expo` 1.7.5 peer-depends on `expo-secure-store` (>=12.5.0), `expo-linking` (>=7.0.0), `expo-network` (>=8.0.7), `expo-constants` (>=17.0.0), `expo-web-browser` (>=14.0.0), plus `better-auth ^1.7.5` and `@better-auth/core ^1.7.5`. SDK 57 satisfies every floor. The server also needs `@better-auth/expo`, not just the app. (https://registry.npmjs.org/@better-auth/expo)
- Whether the anonymous session cookie reaches `GET /magic-link/verify` on a real device is **(unverified)**: that GET comes from a deep-link-opened browser, not the app's fetch, so the SecureStore cookie is not attached and there is no OAuth-state fallback for magic link. The Workers test will pass while the device flow does not.

## Decisions the orchestrator must take

1. **Fail-closed config block.** Set `rateLimit.enabled: true`, assert `BETTER_AUTH_SECRET` is present and >= 32 chars in `createAuth`, and set `advanced.ipAddress.ipAddressHeaders: ['cf-connecting-ip']`. Trade-off: three lines of config and two tests, versus shipping with rate limiting off, a public default signing key, and one shared global rate-limit bucket.
2. **Rate limit storage.** Recommend `customStorage` over the existing `USER_RL` Durable Object; if that is too much for increment 5, keep `'database'` as a documented interim and prove the `lastRequest` bigint round trip first. Trade-off: a DO to write now, versus a Postgres read plus write on every auth request resting on an unverified driver behaviour.
3. **Apple native route shape.** Register it as a Better Auth plugin endpoint at `/sign-in/apple-native`, verify the token and exchange the code yourself, then call `handleOAuthUserInfo` and `setSessionCookie`. Trade-off: depends on two subpath exports with no documented stability guarantee, versus hand-rolling HMAC cookie signing and silently losing the anonymous merge because `/apple/native` does not match the hook prefix.
4. **Nonce enforcement.** Add a before-hook on `/sign-in/social` rejecting an `idToken` body with no `nonce`. Trade-off: one hook and one test, versus an acceptance criterion that configuration cannot satisfy.
5. **Google test seam.** Set `socialProviders.google.verifyIdToken` backed by a module-scope `createRemoteJWKSet` whose URL comes from env. Trade-off: replaces a library code path we then own, and in exchange gets the test JWKS, a JWKS cache the stock provider lacks, and one place to pin RS256 and the audience list.
6. **Google client library.** Switch the mobile side to `react-native-nitro-google-signin` 2.3.0. Trade-off: a younger MIT library on Nitro Modules, versus a paid licence or dropping the nonce requirement entirely.
7. **Merge function.** Extract `merge(from, to, tx)` as an idempotent plain function called from `onLinkAccount` and directly from both native paths, with a replay test. Trade-off: more wiring than one callback, versus a merge that never fires for native Google or Apple and cannot be safely retried after a throw.
8. **Two encryption schemes.** Keep `refresh_token_enc` under `TOKEN_KEK_V{n}` and decide `account.encryptOAuthTokens` deliberately, naming both schemes in the threat model. Trade-off: two rotation drills, versus plaintext provider tokens in `accounts`.
9. **Owner tasks before staging.** Register both `planeahead.app` and `send.planeahead.app` as Apple email sources, and move off the Resend free tier before any real beta. Trade-off: two manual steps now, versus silent bounces for every Hide My Email user and a 100/day ceiling.
10. **Expo deps in Constraints.** Name the five Expo peers plus `@better-auth/core`. Trade-off: none; the spec's "nothing else" is factually wrong.

## Appendix: open questions per research topic

### better-auth-config (53 facts, 2 unverified)

- Apple primary sources could not be read: developer.apple.com pages are client-rendered and WebFetch returned title-only. Verified 'verifying-a-user' through the /tutorials/data/....json endpoint, but the generate-and-validate-tokens page (the authorization_code exchange parameters, the returned fields, and whether the refresh token is returned only once) remains unverified. Confirm in a browser before writing apple-native.ts and apple-client-secret.ts.
- Apple's nonce claim encoding is not confirmed from Apple. Better Auth's 'exact-or-sha256' comparison uses lowercase hex SHA-256, and community reports agree, but no Apple page states the encoding. A wrong assumption here fails closed (rejected sign-in), so it is testable rather than dangerous, but it should be pinned with a real device token before the acceptance test is written.
- Does rate_limits.lastRequest survive the postgres.js to Drizzle bigint({ mode: 'number' }) round trip through Hyperdrive? Carried over unresolved from increment 3 and it now gates the choice of rateLimit.storage: 'database'. Better Auth compares lastRequest arithmetically and uses it in an incrementOne guard, so a string silently breaks both the window reset and the burst guard. One insert-and-read test settles it.
- Does Better Auth ever read or write rate_limits outside the paths the drizzleAdapter maps, and does its rate-limit create path supply an id or rely on the column default? Not traced at 1.7.5. Moot if the column carries DEFAULT uuidv7().
- What is the actual encoded size of the compact session_data cookie for a PlaneAhead user, and does it chunk? getChunkedCookie exists, so chunking is supported, but the Expo client stores one cookie string in SecureStore and the multi-chunk replay path was not traced. If it chunks, the native session cache may silently degrade.
- Does the anonymous session cookie reach GET /magic-link/verify on a real device? The verify request is a GET from a deep-link-opened browser, not from the app's fetch, so the SecureStore cookie is not attached and resolveAnonymousSession has no OAuth-state fallback for magic link. The Workers test (which drives cookies directly) will pass while the device flow does not. Needs a device or Expo Go check before the merge is called done.
- Should GET /api/auth/expo-authorization-proxy be blocked at the Hono layer? Adding expo() registers it, and its own source carries a FIXME saying it still permits redirects to unrelated external https hosts. The Expo client sets x-skip-oauth-proxy: true, so PlaneAhead may never need it. Needs an explicit decision recorded in docs/security/threat-model.md.
- Resend's documented requests-per-second limit was not found on the API reference page. Low urgency at the spec's 3/hour/email cap, but worth pinning before any bulk or transactional fan-out.
- Measured bundle and CPU delta of better-auth/minimal versus better-auth under the Workers build was not taken. The Kysely exclusion is a source-level fact, not a measured saving.
- Whether the deprecated top-level advanced.generateId is still honoured in a way that could shadow advanced.database.generateId if both are present. create-context checks the deprecated one first, so setting both would silently prefer the wrong one. Set only advanced.database.generateId; no further work needed unless someone adds the other.

### better-auth-internal-session (31 facts, 0 unverified)

- Does the mobile client call POST /api/auth/sign-in/apple-native through the Better Auth Expo client's fetch, or through the plain Hono AppType client? The Expo client strips the stored session cookie from any request whose body has an `idToken` key, which would break the anonymous merge. The spec's field name is `identityToken`, which avoids it, but only by accident. Needs an explicit decision plus a test that asserts the anonymous cookie reaches the route.
- Whether setSessionCookie is considered stable public API. It is exported from the 'better-auth/cookies' subpath and used by every first-party plugin, but the plugin docs page never shows it, so it has no documented stability guarantee. Not verifiable from the sources available; treat the 1.7.5 pin as the mitigation.
- Whether ctx.context.newSession and the anonymous after-hook behave identically when a plugin endpoint is invoked via auth.api.* rather than through the HTTP router. dispatchAuthEndpoint runs the same hook pipeline in both cases from source reading, but this was not executed, so it is unverified in practice.
- The exact error code Apple returns from /auth/revoke when the refresh token has already been invalidated by the user in their Apple ID settings. The docs say 400 with an error code description but the enumeration of codes was not retrievable, so the deletion path's retry/ignore policy is unverified.
- Whether accounts.refresh_token_enc being written after handleOAuthUserInfo's transaction commits can be made atomic. runWithTransaction is internal to that function and takes no caller-supplied transaction, so a crash between step 3 and step 5 leaves an Apple account with a session and no revocable token. Unverified whether ctx.context.adapter's transaction can be entered around the call instead.
- Whether Better Auth's runtime schema check (advanced.database.validateSchema, per increment 3 facts) tolerates the extra accounts.refresh_token_enc and key_version columns. They must be nullable or defaulted; refresh_token_enc will be null between user creation and the encrypted write, so nullable is required, not optional.

### apple-google-tokens (51 facts, 0 unverified)

- Exact date Apple switches new Sign in with Apple addresses to private.icloud.com. The 2026-08-24 announcement says only "starting later this year" and gives no cutover date, so we cannot schedule the allowlist change against a deadline.
- Whether appleid.apple.com/auth/keys and googleapis.com/oauth2/v3/certs return Cache-Control headers that let the Cloudflare edge cache actually serve the JWKS across isolates. Cloudflare documents that a Worker fetch reads through cache for third-party hosts, but I did not check the response headers, so the second cache layer is assumed rather than verified.
- Whether Cloudflare Workers Web Crypto importKey accepts the pkcs8 format for ECDSA P-256 specifically. The supported-algorithms table marks ECDSA importKey as supported but does not enumerate curves or key formats. Settle it with a one-line unit test importing the dummy APPLE_SIWA_P8 from .dev.vars.test before writing apple-client-secret.ts.
- The price and licence terms of @react-native-google-signin Universal Sign In. The docs link to universal-sign-in.com/license and say "Buy a license" but publish no figure. Only matters if recommendation 1 is rejected.
- Whether Apple returns the email claim on every native sign-in or only on first consent. Apple documents that it can be empty for Work and School accounts but does not state the behaviour across repeat native authorizations. Better Auth throws UNAUTHORIZED / USER_EMAIL_NOT_FOUND when it is missing, so this needs a decision on the fallback before it surfaces as a production 401.
- Whether the nonce passed through GoogleSignIn-iOS 9.0.0+ reliably appears as the nonce claim in the returned ID token. The release note says "Allow providing a custom nonce via GSI to AppAuth" and the OIDC spec and Google's claim definition imply it, but Google publishes no iOS-specific statement, and its iOS backend-auth verification checklist omits nonce entirely. Confirm empirically on a device before writing the assertion into the Workers test.
- Whether to keep or clear accounts.id_token after the Apple native sign-in. Better Auth writes the raw identity token there in plaintext. It is short-lived and only carries sub plus email, but it is inconsistent with the increment's stated posture of encrypting every provider secret at rest.

### webcrypto-envelope (26 facts, 5 unverified)

- Is crypto.subtle.importKey actually permitted at true module top-level in production, or only in the deferred sense? workerd source shows no IoContext acquisition, so it should be, but I did not run it. It is moot if the provider is a lazy handler-time memo, which is what I recommend, since env is not reachable at module scope without the cloudflare:workers env import.
- What exactly does the nodejs_compat page say about the 2026-08-04 compatibility date enabling nodejs_compat and nodejs_compat_v2 by default? I read it from a page summary, not the raw source. Re-read before pinning compatibility_date in wrangler.jsonc, since the Buffer decode path depends on it.
- Does @cloudflare/vitest-pool-workers enforce the same global-scope entropy restriction as production? There is an open workers-sdk issue (https://github.com/cloudflare/workers-sdk/issues/12886) reporting that global-scope restrictions are not enforced under the Vite plugin during dev. If the test runner is more permissive than production, a module-scope getRandomValues bug passes CI and fails on deploy. Add a deploy-path smoke test or an ESLint rule.
- What does Better Auth 1.7.5's account.encryptOAuthTokens actually use for key derivation, and does it collide with our key_version scheme? This was left open in the increment 3 facts sheet (section on open questions) and increment 5 decides whether we rely on it or keep refresh_token_enc as the only encrypted store. Needs a read of packages/better-auth/src/crypto at v1.7.5.
- What bytea round-trip behaviour does drizzle-orm 0.45.2 have over postgres.js for the wrapped_dek and ciphertext columns? Carried from the increment 3 open questions; rc.1 fixed a bytea corruption bug on neon-http, so the mapping is demonstrably driver-sensitive and every envelope column is bytea.
- Does jose 6.2.12 expose A256KW and A256GCMKW on the Workers runtime? The README says Cloudflare Workers is supported and that some algorithms vary by runtime, with per-runtime algorithm lists kept in separate issues that I did not read. This only matters if someone proposes JWE as an alternative to the hand-rolled envelope; the direct WebCrypto path needs no answer here.
- Should the AAD include the key_version, not just table, column and rowId? As specified, a ciphertext re-wrapped under a new KEK keeps the same AAD, which is correct for rotateKek (re-wrap only), but it means AAD cannot detect a version-downgrade attempt on the DEK. Probably fine, but it is a deliberate choice that should be written down in docs/security/threat-model.md rather than left implicit.
- Where does the plaintext DEK live between unwrap and use, and is that acceptable? A CryptoKey's material is not reachable from JS, but the 32 raw bytes exist in the isolate heap during generation before import. There is no zeroisation primitive in WebCrypto and none in Workers. This is a threat-model paragraph, not a code change, but it should be stated rather than discovered later.
